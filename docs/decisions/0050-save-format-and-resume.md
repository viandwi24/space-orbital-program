# 0050 — Save format: plain versioned JSON, bodies rebuilt on resume

**Status:** accepted
**Date:** 2026-10-17
**Plan:** plans/043-save-and-load-game.md
**Builds on:** ADR 0010 (state in the world), 0017 (flight frames), 0024 (surface rails), 0041 (IndexedDB library), 0048 (v1 scope), 0049 (SAS state is plain data).

## Context

Closing the tab loses the flight. v1 needs quicksave, autosave, named saves and files. The sim keeps nearly all state in the world as plain components (ADR 0010); outside it live the clock, the accumulator, the PRNG and, in each flight frame, the Rapier bodies with their float32 pose and the contact solver's private state. Research (`research/save-and-load.md`): IndexedDB quota is large and eviction is the real risk; structured clone handles plain data; Rapier is deterministic for the same construction order but has no documented restore.

## Decision

1. **`Sim.save(): SimSave` and `createSim({ resume })`** (additive; API 0.1.12). A `SimSave` is plain JSON-compatible data: `format: "orbital-sim-save"`, `formatVersion` (1), `apiVersion`, `mods` (id and version of every booted plugin, boot order), `body`, `dt`, `seed`, `time`, `warp`, `accumulator`, `rng` (the 32-bit state), `world` (`world.serialize()`), `frames` and a `checksum`.
2. **Essential versus derived.** Saved: the whole world (vessels, parts, module states, SAS, rails elements, temperatures, rest and idle counters), the clock, the PRNG, and per flight frame its origin and velocity and per body the pose of its origin, the rotation, the linear and angular velocity of the centre of mass and the mass properties last pushed to the backend. Derived and rebuilt: Rapier bodies and colliders (`createVesselBody` with the saved pose and mass properties, in the saved creation order), ground tiles (the first step recreates them), snapshots, the cached `com`/`velocity` (they are in the world), `core.pending` and `core.active` (empty or recomputed within a step), anything in the renderer or HUD. Not saved: scripts (a script stops on load; its text lives in `localStorage` as before), thumbnails and names (the web client's envelope).
3. **Bodies are rebuilt, not snapshotted.** The pose read back from Rapier is float32 widened to float64, so writing it into a new body is exact. Rapier's `takeSnapshot` is not used: it is an engine-internal byte format tied to a Rapier build and would make saves unmigratable.
4. **Resume equals uninterrupted: exactly, except in ground contact.** Byte for byte (snapshot, serialised world, clock, PRNG compared as JSON text every simulated second) for mid-ascent under thrust, right after staging, on orbital rails, on surface rails and through a wake, and during an SAS hold. A body touching its ground tile (on the pad, landed) cannot be reproduced exactly: Rapier warm-starts the contact solver from impulses it keeps privately, and a rebuilt body starts cold. Measured: a vessel at rest on terrain jitters at about 3e-4 m/s in either direction (the resumed run's sign differs), which gives position, velocity and angle differences below 1.3e-3 (m, m/s, rad) over the next 6 to 8 s and stays flat while the vessel rests. On flat ground the difference measured 4e-9 through a lift-off. **The tested bound is 5e-3 in the units of each value, while any body touches the ground tile.** Every discrete value (modes, stage counters, booleans, strings, ids) must still match exactly; the derived orbital elements are left out of the tolerant comparison because the elements of a near-equatorial orbit are ill-conditioned (journal 002). An unguided rocket lifting off after such a resume diverges from the uninterrupted flight exponentially (1 cm after 15 s, 0.8 m after 30 s): that is the sensitivity of the flight, not an error of the save, and the tests state the horizon.
5. **Validation at the boundary.** `readSimSave` (core) runs on every save read from a file, storage or `postMessage`: marker and version (foreign file: "not an Orbital save file"; newer: "update the game"), the checksum of the bytes the file was written with (edited or cut: "damaged"), the migration chain, then a structural schema. `createSim` additionally checks the sim components (vessel and part shape, consistent mode and rails, every part and module registered, every flight vessel in exactly one frame body) and refuses with a `SaveError` whose `code` is `not-json | not-a-save | too-new | damaged | missing-mod | incompatible`. The checksum is a 53-bit hash for accidents, not tamper protection: saves are the player's own data and a hand-edited save is allowed to be invalid in game terms.
6. **Migration policy.** `SIM_SAVE_VERSION` is bumped by any change that an older reader or the new resume code cannot handle: removed or renamed fields, changed meaning, new required fields. A bump comes with a step in `SIM_SAVE_MIGRATIONS` (keyed by the version it upgrades from, pure, run in order, the result re-signed), an ADR, and a frozen fixture of the old version kept under `packages/sim/test/fixtures` that the tests still load. Additive optional fields do not bump. Version 1 is the first format; its fixture `save-v1.json` is frozen.
7. **Mods.** A save lists its plugins. Resume refuses a save whose plugin id is not loaded (`missing-mod`, naming the mod) and any part or module id absent from the registries; a different version of a loaded plugin is allowed and the web layer shows a notice. State that a plugin keeps in closures instead of the world (forbidden by ADR 0010) is not saved. Plan 046 must show the list in the mod manager and keep ids stable.
8. **Time warp and rails.** A save taken at warp N resumes at warp N; the accumulator is saved, so the fractional step is not lost. Saving never changes the sim (the test compares a resumed sim's own save with the one it was made from, byte for byte).
9. **Web client envelope** (`apps/web/src/lib/save`): `{ format: "orbital-game-save", formatVersion, id, name, kind: quick | auto | manual, createdAt, summary, thumbnail, focus, mods, sim }`. Storage is IndexedDB (database `orbital`, store `saves`, `keyPath: id`) behind a `SaveStore` interface, as ADR 0041; slots: one quicksave, a rotation of three autosaves, any number of named saves; a quota or write error leaves the previous save untouched and is reported; export and import as a `.orbital-save.json` file.

## Alternatives considered

- **Rapier `takeSnapshot`** for bit-exact contact states — rejected (point 3); it would also contradict the plain-data rule the project set.
- **Replaying the command log from the start** — rejected: unbounded time to load, breaks on any sim change, and scripts make the log huge.
- **A warm-up step on resume** (re-stepping the last step to rebuild contacts) — rejected: it would apply module hooks and propellant use twice, and still would not reproduce the old impulses.
- **Saving only a vessel list and re-launching** — rejected: loses debris, other vessels, warp, time.

## Consequences

- Plans 044 and 046 extend the save by keeping their state in the world (a second body's vessels, SOI in `VesselState.soi`, maneuver nodes as components) or by bumping the version with a migration; plan 044 must add its body list to `SimSave` (today one root body, `body`).
- Tests of exact resume are mandatory for any new sim state (`test/resume.test.ts`).
- The tolerance in point 4 is a measured property of Rapier's solver, to be re-measured when Rapier is upgraded.
