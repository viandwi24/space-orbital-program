# 0292 — The mod World API: one query facade, gated commands, stores, an events catalogue, keys and notices

**Status:** accepted (owner's question, 2026-10-22)
**Date:** 2026-10-22
**Plan:** plans/343-mod-world-api.md
**Amends:** ADR 0013 (SDK surface), ADR 0149 point 2 (panel input), ADR 0271 point 4 (autopilot signature)

## Context

The owner asked whether a mod can reach the whole game, for example "get all entities". Mods can register almost any content and can run code per part (modules), per vessel (autopilots) and per step (systems). But a system only gets the raw ECS `World`, whose components are sim internals; panels get the raw snapshot; nothing lets a mod act on the world as a whole, keep its own saved state, give the player a key, or show a notice outside its panel. Mods are trusted code (ADR 0057), so the question is not sandboxing but a stable surface: what mods read must not break when the sim's internals change, and what they do must obey the world's rules like the player's commands do.

## Decision

1. **`WorldQuery`, one read-only facade over the snapshot.** `createWorldQuery(snapshot, bodies?)` (core, exported by the SDK) answers in plain types (`WorldVessel`, `WorldPart`, `WorldBody`, …): `vessels(filter)` by type, situation, SOI, owner and distance; `vessel`, `findVessel`, `nearest`, `distance`; `parts`, `resources`, `crewOf`, `orbit`, `comms`; `bodies`, `body`; `sites`, `crew`, `economy`; `time`, `paused`, `day`, `rule`, `store`. It is built from the same `Snapshot` the page gets, so it is the protocol's stability, not the ECS's. Systems and autopilots get it as `ctx.world` (built lazily, once per sim time, only when read); panels as `input.world`. The raw `World` stays for module state.
2. **A coarse situation.** `VesselSituation` is `prelaunch | landed | splashed | flying | sub-orbital | orbiting | escaping`, from the snapshot and the body (top of the air, SOI radius). The sim sets `VesselSnapshot.situation` and emits `vessel:situation-changed { vessel, from, to, body, time }` when it changes: a vessel in physics is checked at most every 0.5 s of sim time, one on fixed rails when its conic's size or shape changes, any at once after an SOI or mode change; with nothing in physics the check runs only after a vessel event or a command, so a long warp pays nothing per chunk.
3. **`ModCommands`, the sim's commands with source `mod`.** `send(command)` plus typed helpers (`setTarget`, `stage`, `actionGroup`, `throttle`, `sas`, `warp`, `warpTo`, `placeNode`, `removeNode`, `addAlarm`, `rename`, `engage`, `disengage`, `spawn`, `terminate`, `focus`). Every call goes through `dispatch`, the handler the keys and scripts use, with the program source the autopilots use (ADR 0276): the player's override and the signal delay apply as to an autopilot, and a replay regenerates the commands from the mod code as it does an autopilot's. Allowed: vessel control, targets, staging, action groups, warp, nodes, alarms, names, autopilots. **Spawn (`load-vessel`), terminate, recover and every `debug-*` command are refused unless debug tools are allowed** (rule `stock.debug-tools`: always in sandbox, or debug mode on, ADR 0213); economy, contracts, research, crew and building commands are refused: a mod that wants to change a career defines content (charges, contracts) the player chooses. `focus(vessel)` emits `mod:focus`, which the page follows like a vessel switch.
4. **Stores: a mod's own saved state.** `defineStore({ id, schema, initial })` (registry `stores`, id `<plugin>.<name>`). `ctx.store(def)` gives `{ get, set, update }` to the owning plugin's systems and autopilots only; `set` validates with the zod schema and refuses JSON over 64 KiB. Values are saved in `SimSave.stores` (optional, no format bump) and checked again on resume: a value that no longer parses falls back to `initial`; a store no loaded mod registers is kept untouched. The snapshot carries `stores` so panels read them (`input.world.store(id)`).
5. **Events: the `EventMap` is the contract, `SIM_EVENTS` is its catalogue.** Each sim event has an entry `{ name, group, description }`; a test fails when an emitted event has none. Systems may declare `on: { 'vessel:docked': (e, ctx) => … }`, subscribed by the sim with the system's context; `update` and `phase` become optional for such a system.
6. **Keys and notices.** `defineKeybinding({ id, label, defaults, mode?, command? })`: the page lists it under Controls → Mods, rebindable with clash checks against flight keys; pressing it sends `command(input)` when given, else the command `mod-key { key, vessel }`, which the sim turns into `mod:key` for systems. `ctx.notify(text, { tone, vessel })` emits `mod:notice`, which the page shows as a toast (only for the active vessel when `vessel` is set).
7. **Versioning.** API 0.1.106; all additions. `AutopilotDefinition.start` and `step` take the context as an extra last argument, so existing autopilots are unchanged.

## Consequences

- "Get all vessels" is `ctx.world.vessels()`; "all landed probes around the Mun" is `ctx.world.vessels({ type: 'probe', situation: 'landed', soi: 'stock.mun' })`.
- Building a full snapshot costs; a system that reads `ctx.world` every physics step pays it each step. The guide says to read it on a world tick, on events or at a low rate.
- The commands a mod may send are two lists in the sim (`MOD_ALLOWED`, and `MOD_DEBUG` for those that need debug tools, in `packages/sim/src/mod-runtime.ts`); widening them is a new ADR.
