# Simulation

`@orbital/sim` drives the world. It is a library: `await createSim(options)` returns an object with `step(wallDelta)`, `dispatch(command)` and `snapshot()`, and no knowledge of where it runs (Bun, Worker, main thread). Shipped by plan 007; decisions in ADR 0015 (module capability API), 0016 (design format, protocol) and 0017 (flight model). Code: `packages/sim/src` (`sim.ts` loop and API, `commands.ts`, `vessel.ts`, `frames.ts`, `modes.ts`, `orbit.ts`, `resources.ts`, `hooks.ts`, `snapshot.ts`, `aero.ts`, `thermal.ts`, `atmosphere.ts`, `parts.ts`, `mass.ts`, `state.ts`). Rigid grouping: ADR 0018. Ground contact, landing legs and impact damage: ADR 0019. Debris and time warp: ADR 0021. Terrain heights shared with the renderer: ADR 0043. Body tree, frames and sphere-of-influence transitions: ADR 0051; the stock moon: ADR 0052. Re-entry heating: ADR 0023. Radial attachment, part yaw, boosters and fins: ADR 0034 and 0035.

## API

```ts
const sim = await createSim({
  plugins: [Stock],                                 // booted with loadPlugins; needs a root body (moons are bodies with a parent and an orbit)
  backendFactory: () => createRapierBackend({ solverIterations: 16 }),  // sync or async; called once per flight frame
  seed: 1,                 // PRNG seed (sim.rng); nothing in the sim draws from it yet
  dt: 0.02,                // fixed flight step
  maxFlightFrames: 2,      // physics backends created up front
  maxStepsPerCall: 5000,   // fixed steps per step() call; the rest stays in the accumulator
  terrain: createBodyTerrainField,  // optional (ADR 0043, 0067): heights of the ground; absent = the flat sphere. A field for the root body's, or (body, world) => field | undefined asked for every body with the world's terrain seed and the flat zones of the sites on that body (plan 084, ADR 0142); `createBodyTerrainField` follows each body's `terrain` kind (hills with the world's seed and zones, craters with a seed, none)
});
sim.step(wallDelta);       // host time in seconds; scaled by warp
sim.dispatch(command);     // -> { ok: true, vessel? } | { ok: false, reason }; never throws on bad input
sim.snapshot();            // plain data, built on request
sim.save();                // the whole run as plain JSON data (plan 043, ADR 0050); createSim({ resume: save, plugins, backendFactory }) continues it
sim.world; sim.events; sim.registries; sim.report; sim.rng; sim.time; sim.warp; sim.dispose();
```

`step` adds `wallDelta × warp` to an accumulator. While any vessel is in flight it runs fixed steps of `dt` (one backend step each, per active frame); with every vessel on rails it advances in analytic chunks of at most 10 s. A host that calls `step(0.02)` at warp 1 gets exactly one fixed step per call, which is what the tests do; a render loop passes its frame time. `dispose()` frees the backends (Rapier WASM). The sim never reads a clock.

## Loop

```
accumulator += wallDelta * warp
while accumulator >= dt:
    if any vessel in flight:   flightStep(dt)       # also advances rails vessels' time
    else:                      railsStep(min(accumulator, 10 s))   # cut at each day boundary
```

**World tick (plan 082, ADR 0171).** Once per game day the sim runs the `world-tick` phase (`packages/sim/src/tick.ts`). A day is the root body's `rotationPeriod` (stock 21 600 s). The day at `t` is `epoch.day + floor(epoch.fraction + t / day)`, and day `n` begins at `(n − epoch.day − epoch.fraction) × day`, computed from `n`, never accumulated. `railsStep` cuts a chunk at the next boundary and sets `t` to it exactly, so at warp 1e6 a 10 s chunk runs its tens of ticks one by one, in order. `flightStep` is not split: a boundary it crossed ticks at the end of the step (at most 20 ms late), with the exact boundary `time`. A tick runs, in this order: the `background` closed forms of every vessel on rails, the world-tick systems (`order`, then plugin boot order, then id; each with `dt = day` and `ctx.tick = { day, time, rng }`, where `rng` is `createRng(streamSeed(worldInfo.seed, system.id))`), then the `world:tick` event `{ day, time }`. `SimCore.ticks` holds the last day entered and the streams.

**Background operations.** A module's `background(ctx, dt)` is a closed form over the time since the vessel's `backgroundAt`. It runs on each tick, when the vessel wakes into flight (before its bodies are made) and before `sim.save()`. A module that declares it gets no `updateOnRails` calls; modules without it keep the per-chunk `updateOnRails`. Only vessels with such a module carry `backgroundAt`: it is set when the vessel is loaded on rails or goes on rails, and removed when it wakes.

`flightStep`: run `pre-physics` systems; per active frame: mass properties → backend (when a part mass changed), gravity, the ground tile moved under the vessel, every module's `update` (thrust, torque, propellant), drag; `backend.step(dt)`; advance the frame origin; ground contact readback (`landed`, impacts) and damage; re-anchor; refresh vessel poses; apply queued `detach` requests (splits, after the step so no queued force is lost); then `updateOnRails` for rails vessels, `t += dt`, `post-physics` systems, idle bookkeeping and automatic rails transitions.

## Vessel modes

| Mode | What runs |
|---|---|
| **flight** | one compound rigid body per vessel in a flight frame (a box collider per part, plus module colliders), gravity at the centre of mass, drag per part, real ground contact on a ground tile, modules' `update` |
| **on-rails** | centre-of-mass state from the stored Kepler elements (or state vector), attitude frozen, modules' `updateOnRails`, no backend. **Surface rails** (ADR 0024): the pose is stored in the body-fixed frame and turns with the planet |

- flight → on-rails (`modes.ts`): automatically, when no module applied a force or torque for 2 s, the vessel is not in ground contact, and its periapsis radius is above `R + atmosphere.height` (`R` for an airless body). The state is the centre of mass; `kepler.fromStateVector` provides elements, and when it throws `KeplerError` (near-parabolic) the state vector is kept and propagated with `propagateUniversal`. Radial states have periapsis 0 and never go on rails. A `state` placement in a stable orbit is created on rails directly.
- **Debris** (ADR 0021; vessels with no `controlSource` part, `isControlled` in `core.ts`; `modes.ts`: `ballisticEligible`, `reapDebris`): (1) idle for 2 s, not landed, more than 400 m up, not in a stable orbit and either climbing or at/above the atmosphere top -> on rails (`vessel:mode-changed` reason `ballistic debris`); a descending vessel below the atmosphere top stays in flight and crashes with `part:damaged` as in plan 012. (2) On rails and not in a stable orbit, it is destroyed (`vessel:destroyed`, reason `debris re-entered the atmosphere`) when it descends below the atmosphere top or reaches the surface, checked at the end of every step (rails chunks are up to 10 s). (3) In flight, touching its ground tile, idle for 10 s (`DEBRIS_REST_TIME`) and slower than 0.1 m/s relative to the ground (`DEBRIS_REST_SPEED`): put on surface rails and kept (plan 223, ADR 0208; until then it was destroyed). (4) The debris cap (`set-debris-cap`, a player setting the page sends each session, default 250, not saved; `fleet.ts` `enforceDebrisCap`) removes the oldest debris (lowest entity id) beyond it, after every step's pass; 0 removes debris at once. Controlled vessels are never touched. Rails have no drag, hence the cut at the atmosphere top. Limitation: debris circling inside the atmosphere (neither climbing nor above it) stays in flight until drag brings it down.
- **Surface rails** (ADR 0024, plan 016; `modes.ts`: `trackRest`, `surfaceEligible`, `toSurfaceRails`; `orbit.ts`: `surfaceRails`, `orientationOf`): a controlled vessel that is `landed`, had no force or torque, and moves slower than 0.05 m/s and spins slower than 0.01 rad/s relative to the ground for 2 s (`SURFACE_REST_TIME`; `VesselState.rest`) goes on `RailsState` kind `surface` (centre of mass and root orientation in the body-fixed frame; reason `at rest on the ground`). Position is `Ry(omega t) r`, velocity `omega x r`, orientation `Ry(omega t) q`; nothing is integrated, so any warp length is exact. The snapshot has `mode: 'on-rails'`, `surface: true`, the root part's pose and ground-fixed velocity, and no `orbit`. Waking uses the commands below; the body is created at the rails pose with angular velocity `omega`, so it neither falls nor pops. Uncontrolled vessels get it only through the debris rule (3) below the debris bullet. Limitation: no colliders on rails, so other vessels pass through a parked one.
- on-rails → flight: a `throttle` > 0, non-zero `attitude`, `stage` or `action` command at warp 1 (the state at time `t` is propagated and bodies are created in a frame). Refused when warp > 1 or no frame is available.
- **Making room** (plan 257, ADR 0250; `modes.ts`: `makeRoomAt`, `roomBlocker`): a wake, a `load-vessel` into flight (a launch) and Debug's set location that find every frame held by vessels far away first free one: a frame whose vessels are all landed (surface rails) or in a stable orbit (rails) goes on rails (reason `making room`), else one where the rest is uncontrolled debris in the air (ballistic rails, reason `ballistic debris`; ADR 0021's re-entry rule then takes it). A controlled vessel in the air keeps its frame; the refusal names it and says to land it, reach orbit, or recover or end it in the Mission Center. Flight shows a launch refusal as **Launch refused** with Back to the VAB and Mission Center, not as a stopped simulation.
- Elements are re-based (`epoch := t`, `m0` folded) whenever `n·(t − epoch) ≥ 2π`, so long warps keep float64 precision.
- Both transitions emit `vessel:mode-changed` `{ vessel, mode, reason }`. Other events: `vessel:created` `{ vessel, from? }`, `vessel:destroyed`, `stage:activated`, `part:damaged` (ground impact or overheating, below).
- **Launch-site coordinates** (plan 025, ADR 0030; `vessel.ts`: `placeOnSurface`): a `surface` placement's latitude and longitude are **body-fixed**: the inertial position is the body-fixed one turned by `omega * t` about +Y, so a vessel loaded at any time stands on the same ground spot (latitude 0, longitude 0 is the body's +X axis turned with the planet) and the renderer's default launch site matches without inference. Before plan 025 the longitude was inertial and a vessel loaded after about 1 s stood roughly 160 m off. With a terrain field (ADR 0043, plan 031) the vessel stands on the ground plane under that point, **nose along the terrain normal** (a lander on a hillside, not a stack that falls over onto it); in the flat zone around the launch site the normal is the radial and the placement is exactly the old one.
- **Sites** (plan 084, ADR 0142; `@orbital/core` `sites.ts`): `WorldInfo.sites` lists `Site`s (`id`, `name`, `body`, `kind`, `latitude`, `longitude`, `flatRadius`, `blendWidth`, `pads` as east/north metres); a world without sites (every format-5 save before 084) has the **Legacy site** (`sitesOf`). `load-vessel` with `placement: { kind: "site", site, pad? }` resolves the pad to latitude and longitude on the site's body (`padLatLon`) and places the vessel like a `surface` placement there; `{ site: "legacy", pad: 0 }` is exactly the default placement. Unknown sites and pads are refused with the reason.
- **Terrain** (ADR 0043, plan 031; seed and zones plan 084, ADR 0142; `terrain.ts`, `@orbital/core` `terrain.ts`): the same height function the renderer draws. It is generated from the world's **terrain seed** (`terrainSeedOf`: the Legacy seed 20 261 016 for the Legacy world, else the world seed; it seeds the biome map and shifts the noise lattice) with the **flat zones** of the sites on the body (at most 8): every zone is exactly zero within its radius and blends out, clears grassland on the biome map and keeps lakes away; the first zone also gets the scenic massif. The Legacy world reproduces the heights of before 084 bit for bit (`core/test/terrain-legacy.test.ts`, 10 000 golden samples). `createSim({ terrain })` turns BCI positions into body-fixed directions with `Ry(-omega t)` and asks it for the ground tile (above), for `ballisticEligible` (more than 400 m above the *terrain*), for the rails reaper (on-rails debris is destroyed at the terrain height, not only at the sphere) and for `isStableOrbit` (periapsis above `R + max(atmosphere height, terrain.maxHeight)`). Pressure and drag keep the altitude above the sphere (sea level). Surface rails need no change (the body-fixed centre of mass already is on the terrain, so wake-up has no pop). Slope behaviour is the rigid body's (see the ground bullet); there is no slope rule beside it.
- **Time warp:** `warp > 1` is refused while any vessel is in flight (the reason names the vessels) and above 1e6; while warping, commands that need flight and `load-vessel` into flight are refused. A controlled vessel idle in a stable orbit reaches rails after two seconds, which is how a player gets to warp. Debris does not hold warp back (ADR 0021, plan 013): see below. A controlled vessel at rest on the ground goes on surface rails after 2 s (ADR 0024, plan 016), so warp works on the pad and after landing.

## Bodies and spheres of influence (plan 044, ADR 0051)

`core.bodies` is the tree of registered bodies (`BodyDefinition.parent` + `orbit`): the root rests at the origin of the system frame, a child follows its Kepler orbit around its parent (`bodies.ts`: `stateInParent`, `systemPosition`), with the Laplace sphere of influence `soiRadius(a, m, M)`. A vessel's state (`com`, `velocity`, rails elements, snapshot position) is **relative to its SOI body** (`VesselState.soi`); a flight frame is centred on one body (`FlightFrame.soi`) and a vessel is only put in a frame of its own SOI. Gravity, rotation (surface rails, ground tile, drag co-rotation), atmosphere, terrain and the SAS surface reference all use that body. `Snapshot.bodies` lists the root first, each with its position in the system frame, so `bodies[soi].position + vessel.position` is the vessel in the system frame.

**The home body and the Sun (plan 122, ADR 0119).** The sim's home (`SimCore.root`, `Sim.home`: terrain, the launch site, recovery, crew, milestones) is `options.body`, else the save's `home`, else the world's primary site's body, else the first body without a parent; it is not the tree's root. The stock root is the Sun (`stock.sun`, `star: true`, no terrain is asked for a star); the home planet orbits it at 13.6 Gm with its pole on the system +Y and the orbit inclined by the tilt (23.44°), so every state in the home sphere is what it was (`test/sun-parity.test.ts` against the frozen flight). Its sphere of influence is now finite (about 84 000 km); a vessel can leave it into the Sun's. Body positions in snapshots are Sun-centred; `stateInParent` keeps the last time and state of each body (a step asks for the same instant many times).

After every step (`soi.ts`, `applySoiTransitions`): a vessel leaves a child for its parent when `|r| > soi`, and enters a child of its body when `|r - r_child(t)| < soi_child`. **On rails** the crossing time is found by bisection inside the step (`core.trajectory.crossing`, the provider's `findCrossing`, 1e-7 s), the state is converted there (`intoChildFrame` / `intoParentFrame`: translate position and velocity by the child's state) and new elements start at the crossing. **In flight** the frame is re-based: its `origin` and `velocity` are translated by the child's state, local poses and velocities are untouched (every frame has the same axes), gravity of the new body applies from the next step; the frame's focus vessel (first controlled, else first) decides for all vessels in it. Event `vessel:soi-changed { vessel, from, to }`; for a controlled vessel `warp` becomes 1 and the rest of the step's accumulator is dropped. `load-vessel` accepts any registered body in `placement.body`. `kepler.predictPatchedConics(bodies, start, horizon)` applies the same rule to a state and returns one conic segment per sphere (entry and exit state, elements, the body's offset in the system frame, why it ends); the map view and plan 045 draw and plan with it, and `test/soi.test.ts` checks it against the sim's crossings and periapsis.

**Trajectory provider (plan 080, ADR 0173).** Every orbit prediction goes through one `TrajectoryProvider` (`@orbital/kepler`, `trajectory.ts`), bound to the body list: `predict`, `predictWithManeuvers`, `stateAt`, `bodyState`, `propagate`, the track helpers, `closestApproach`, `closestApproachOnTrack`, `conicClosestApproach` and `crossing`. `createSim` builds `SimCore.trajectory` with `createTrajectoryProvider(worldInfo.gravityModel, bodies)`. Only `patched` exists, and an `n-body` world is a `SaveError` (`incompatible`, "n-body worlds are not available yet"). The sim's node prediction, SOI crossings and target approach call it. The web client's map path and rendezvous aids reach it through `trajectoryFor(bodies)`, one cached provider per body list. The patched provider forwards to the existing functions unchanged, and goldens recorded before the move (`packages/sim/test/trajectory-golden.test.ts`, `apps/web/src/lib/trajectory-golden.test.ts`) pin the numbers. A rails state is a single conic by definition, so `railsMotion` and `stateInParent` still propagate it with `kepler.propagate` directly; an n-body world (plan 125) changes the rails representation itself.

**Path models (plan 123, ADR 0183).** `orbit.model` is `kepler` (the default fixed conic on the world's time), `kepler-rates` or `series`:

- `kepler-rates` is elements at `epoch` with SI rates per second and a `meanMotion`. It is JPL Level A, and `levelAElements` converts a Table 1 row.
- `series` is sine and cosine series of ecliptic longitude, latitude and parallax, as in the Almanac Moon.

The J2000 models run on `τ = t + world epoch offset` (`BodyRuntime.timeOffset`). `stateInParent` dispatches through kepler's `bodyPathState` and caches per time. Code that needs a conic takes `elementsAt(body, t)`, the osculating elements now: the target's approach, and the trajectory provider's body list, refreshed after every step (`refreshPatchedBodies`). SOI crossings bisect on `stateInParent` as before, so an entry follows the real path. The elements in `orbit` stay the mean conic, which sizes the sphere of influence. Scripts, the planner and the renderer read the mean conic until 124.

**Systems (plan 124, ADR 0184).** `createSim` loads the plugins with the world's system and variant, so `sim.registries` holds only that system's bodies, with the variant's patches applied. The home is the asked body, the save's, the primary site's (if loaded), the variant's `home`, or the root. A body with `rotation.epoch: 'j2000'` gets its `w0` and periodic phases shifted by the world epoch in `buildBodies`, so every consumer of the sim's bodies sees world time.

## Frames and precision

See `units-and-frames.md`. BCI float64 is authoritative; flight runs in a local frame that moves at constant velocity (`bci = origin + local`, velocities relative to `frame.velocity`) and re-anchors when the focus vessel is 1 km from the origin. One frame holds a cluster of vessels (a decoupled stage stays with its parent); a vessel loaded or woken within 2.5 km joins an active frame, otherwise it needs a free one (`maxFlightFrames`).

## Vessel design format (`VesselDesign`, `formatVersion` 1, 2 or 3, ADR 0016, 0034 and 0071)

```json
{ "formatVersion": 1, "name": "Two-stage",
  "parts": [
    { "index": 0, "part": "stock.command-pod", "parent": null },
    { "index": 1, "part": "stock.reaction-wheel", "parent": { "index": 0, "parentNode": "bottom", "node": "top" } }
  ],
  "stages": [[6], [4, 3]] }
```

A part may carry `symmetry` (version 2, editor groups) and `mirror: true` (plan 217, ADR 0221: the reflected member of a mirror pair; any version); the sim ignores both. A flat list; `index` is any unique non-negative integer (stable under edits), `parent` names a node of the parent part (`parentNode`) and a node of this part (`node`), `stages[k]` are the indices whose modules' `onStage` runs for the k-th `stage` command (listed order). Validate with `vesselDesignSchema` (shape) and `resolveVesselDesign(design, registries.parts)` (semantics: one root, unique indices, registered parts, resolvable parents, nodes exist and host one attachment, anti-parallel node directions = stack attachment, connected, valid stage references); the latter returns part origins computed from node positions. +Y is the stack axis, the root is the origin. Version 2 (ADR 0034) adds, optionally: a **radial link** `parent: { index, parentNode: "surface", node, radial: { angle, y } }` that hangs the child's horizontal `node` on the side of a cylindrical parent at azimuth `angle` (rad about +Y from the parent's +X) and height `y`, and `symmetry: n` (parts made together share the number; an editing aid the sim ignores). Parts may be turned about +Y only: `ResolvedPart.yaw` is 0 for stack parts (inherited from the parent) and faces the parent's axis for radial parts; thrust axes stay vertical. `migrateVesselDesign` turns older versions into the current one unchanged; radial links and `symmetry` in a version 1 design are refused. Version 3 (ADR 0071, plan 041) adds, optionally: `tilt: { x, y, z }` (rad; the part turns by `Rx Ry Rz` about its parent's axes at the attach point, before a radial part faces the surface, so two wings with the same tilt are mirror images), radial links to **box** parents (the site is the ray from the part axis: where it leaves the box rectangle, facing along that face's normal), and `link: { index, angle, y }` on **connector parts** (`PartDefinition.connector`: struts and fuel lines), the surface point of a second part their far end lands on. `ResolvedPart` also carries `rotation` (full, `tilted` says when it is more than the yaw) and `link.point`; `placeStack`, `placeRadial`, `surfacePoint`, `surfaceSite` expose the geometry for tools. Example: `{ "index": 10, "part": "stock.radial-decoupler", "parent": { "index": 3, "parentNode": "surface", "node": "radial", "radial": { "angle": 0, "y": 0 } }, "symmetry": 1 }`, then `{ "index": 11, "part": "stock.booster", "parent": { "index": 10, "parentNode": "outer", "node": "radial" } }`.

## Assembly and physics

- A vessel and each part are world entities (`sim.vessel`, `sim.part`, `sim.module-state:<module id>` components, ADR 0010); physics handles live outside the world, in the frame.
- **One rigid body per vessel** (ADR 0018, plan 011): a `compound` shape with colliders per part (the shape's box, or 1 m without a shape; a cylinder is four squares inscribed in its circle turned by 22.5° steps, `colliderBoxes`, ADR 0245) at `designPos − root.designPos` (turned by the part's `yaw`); the body origin is the root part's origin, so part poses are `body pose ∘ constant offset`. No joints. Part mass = dry mass + Σ container contents × density; whenever any part mass changed the sim recomputes the vessel's mass, centre of mass and full inertia tensor (parts' own inertia — solid cylinder or box — plus parallel axis; diagonalised by Jacobi into principal moments and a frame, `mass.ts`) and calls `setMass`. A 100-part stack costs one body and about 25 µs of backend time instead of 100 bodies, 99 joints and about 600 µs, and cannot flex.
- Tilted parts and connectors (ADR 0071): `PartState.rotation` (only for a tilted part or one of its descendants; absent means `qAboutY(yaw)`, so older designs and saves are untouched) is the part's full rotation: collider, inertia tensor (`R diag R^T` plus the parallel-axis term), hook forces, `torqueDemand`, `centreOfMass`, separation direction, snapshot orientation and the lowest point at placement all use it. `PartState.link` (`{ peer, point }`) is a connector's far end; a split clears it when the ends land on different vessels (the strut hangs on, the vessel still splits), and `PartSnapshot.link` gives the renderer the point. A strut adds mass and drag only (one rigid body, ADR 0018).
- Part yaw (ADR 0034): `PartState.yaw` turns a part about the vessel's +Y axis. A part's orientation is the body's times its yaw (snapshots, hook forces, drag), its inertia is rotated about Y, its colliders carry the rotation. Hooks get `vessel.airVelocity(point?)` (ADR 0035): the velocity of a point relative to the co-rotating air, in the part frame, including the vessel's spin; `stock.fin` builds its normal force from it.
- Steering (ADR 0045, 0046; plan 033): hooks also get `vessel.centreOfMass` (the body's centre of mass in the part frame, flight only) and `vessel.torqueDemand` (the attitude demand as a torque direction in the part frame, the vessel `control` turned back by the part's yaw). Stock steers with them through one mixing rule (`mods/stock/src/steering.ts`): an actuator whose torque per unit deflection about the centre of mass is `t` takes the fraction `clamp(d . t / |t|, -1, 1) * min(1, |t| / 1 m)` of its range. `stock.engine` with `gimbal: { range, rate }` tilts its thrust vector (the force is `thrust * (sin ax, cos, sin az)` at the part origin, so the torque is `r x F`; snapshot field `gimbal`), `stock.control-surface` turns a fin plate about its span (snapshot `deflection`), and fins add a damping force on the rotational part of the airflow. All of it is deterministic arithmetic in the step; the reaction wheel keeps working in parallel.
- **Stability assist (SAS)** (ADR 0049, plan 042; `sas.ts`): `VesselState.sas` (`mode`, `reference`, hold quaternion, integrator, plain data) and the `sas` command. In `prepareFrame`, before the module hooks, every controlled flight vessel with SAS on gets its target (hold quaternion, or a direction: prograde/retrograde along the `surface` or `orbit` reference velocity, normal/antinormal along `r x v`, radial along `r` - the navball markers) turned into an attitude demand: eigen-axis error, desired rate `min(0.7 e, sqrt(2 * 0.5 * a_max e), 0.6 rad/s)`, rate loop `3/s` plus a bounded integral, normalised by `a_max = authority / inertia` per axis. The authority is the sum of every module's `controlAuthority` (N·m per part axis; stock: reaction wheel, lit gimbal engine, control surface in air) over the diagonal of the inertia tensor, so a probe on wheels, a finned rocket on its bell and a lander all respond at their own best rate without overshoot. The demand replaces `VesselApi.control` pitch/yaw/roll for the modules (`effectiveControl`); a non-zero player `attitude` input overrides it, `hold` then follows the vessel and latches below 0.004 rad/s. A settled vessel (error < 0.003 rad, rate < 0.01 rad/s, no learned integral) gets exactly zero demand until the error exceeds 0.01 rad, so it still goes on rails. On orbital rails a pointing mode sets the attitude analytically each rails step (end of step, after the elements advanced); `hold` keeps the frozen attitude; surface rails are untouched. Staging copies the state to the split-off vessel. `VesselSnapshot.sas = { mode, reference, error }`.
- **Targets** (ADR 0065, plan 035; `target.ts`): `VesselState.target` (`{ kind: 'body', id }` or `{ kind: 'vessel', id }`) set by `target-set`; `resolveTarget` gives the relative state in the shared inertial axes (system-frame states of both ends, bodies by walking the parent chain) and the closest approach (`kepler.closestApproach` over the vessel's next revolution, only for two conics about one body); SAS `target`/`anti-target` read `targetDirection`; `pruneTargets` drops a vanished target vessel after each step (`vessel:target-lost`); a split hands the target to the controlled half.
- **Rendezvous aids** (ADR 0084, plan 057) are not sim state: `kepler/rendezvous.ts` has `patchedTrack` (the patched-conic path as a function of time, also for the path with maneuver nodes), `closestApproachPatched` (the closest approach across spheres of influence to a body or a conic), `matchVelocityBurn`, `hohmannTransfer`/`hohmannToTarget` (departure wait from the phase angle) and `relativeNodes` (where the orbit crosses the target's plane, with the plane-change burn); the web client (`rendezvous-aids.ts`, `target-view.ts`) turns them into `node-set` commands, so a node placed by an aid is an ordinary node in the sim, saves and scripts.
- **Maneuver nodes** (ADR 0056, plan 045; `maneuver.ts`): `VesselState.nodes` (`id`, `time`, planned prograde/normal/radial, `target` = absolute post-burn velocity). The remaining burn is `target - the velocity the vessel's current orbit has at the node time`, resolved with `core.trajectory.predictWithManeuvers` (the function the map view draws with, plan 080); the snapshot reports it, SAS `maneuver` points at the earliest node's burn vector, a passed node with under 0.5 m/s left is removed (`vessel:maneuver-complete`). `warp-to` is `core.warpTarget`: the effective warp is `min(warp, remaining / 1 s)` and the accumulated time is capped so the clock lands on the target; saved in format 3 (`SimSave.warpTarget`).
- Forces: gravity is one force at the centre of mass, drag is applied per part at its origin, module forces act on the vessel body at the part origin (or the given point); a reaction wheel's torque turns the whole vessel.
- Gravity: `a = −μ r / |r|³` as a force on each body, `μ = G·M` of the body the frame is centred on (point mass; one body at a time, patched conics). Rotation: `bodyOrientation(body, t) = q_pole · Ry(W(t))` from `@orbital/core` (plan 085, ADR 0145; without `BodyDefinition.rotation` it is `2π t / rotationPeriod` about +Y, bit for bit as before), read in the sim through `rotationAt(body, t)` and `spinAt(body, t)` (the angular-velocity vector); the launch site, the ground tile, surface rails, stones, the SAS surface reference and the atmosphere co-rotate with it.
- Ground (ADR 0019, plan 012; terrain: ADR 0043, plan 031): the reference sphere, or the terrain above it when `createSim` got a `terrain` field (`@orbital/core` `TerrainField`: `heightAt(body-fixed unit direction)` in metres, `maxHeight`), represented by a **ground tile** per flight vessel whose centre of mass is within 300 m of the ground (dropped again above 400 m; the altitude is measured above the terrain under the vessel, so a vessel resting on a 3 km plateau has its tile and one 1 km above it does not): a kinematic 400 x 400 x 200 m slab whose top face is the tangent plane of the ground under the centre of mass (the terrain point on the radial at `R + h`, the normal from a central difference of `h` over 4 m to each side along east and north; the radial and `h = 0` without terrain; `terrain.ts`), re-positioned every step in the local frame and moving with the rotating ground (linear and angular velocity), friction 0.8, restitution 0. A stack stands on it by friction, tips over, slides and rests on legs; no pad hold, no clamp. **Slopes have no rule of their own**: the tile is a rigid plane, so a vessel slides on slopes steeper than `atan(0.8)` = 38.7 degrees and tips over when its centre of mass leaves the support polygon (a lone pod rests at 38 degrees and slides at 42, a three-part probe tips between 25 and 30, a two-stage stack at 10, a lander with legs out between 10 and 20; `test/terrain.test.ts`). The impact rule below uses the closing speed along the tile normal, so a vertical landing on a 30 degree slope closes at `v cos 30`. `landed` is true while the vessel has contact points (distance <= 2 cm) with its tile, which keeps it off rails. `PhysicsBackend.contacts(a, b)` reads the contact points after the step.
- Stones (plan 060, ADR 0092; `stones.ts`, `@orbital/core` `stones.ts`): on a body whose `terrain.kind` is `craters` a flight vessel whose centre of mass is within 60 m of the terrain (dropped above 80 m) has a second kinematic body next to its tile, one sphere per stone of the lattice (`stonesAround`, the list the renderer draws; the body's craters seed shifts the lattice) within 24 m of where it was built, the 96 nearest at most, each the drawn dome's cap standing on `terrain.heightAt`; fixed to the rotating ground, rebuilt after 8 m of travel, friction 0.8. Contacts count for `landed` and for damage, with the closing speed taken along the stone's normal. Nothing of it is saved; there are none on the home planet or on a `hills` body.
- Damage: a part's impact speed is the closing speed of its contact point against the ground along the tile normal, from the velocities before the step in which the contact appears. Above `impactTolerance` (part data, default 6 m/s) the part breaks off (cut from every neighbour with `splitVessel`; it flies on as debris); above twice the tolerance it is destroyed (removed; an emptied vessel is destroyed). Event `part:damaged { vessel, part, definition, speed, outcome }`. The whole rigid body is stopped by the same contact, so the parts above an impacted one are not damaged by the impact itself. Part-to-part collision damage is not modelled.
- Landing legs are module colliders (`ModuleDefinition.colliders`): `stock.landing-legs` adds four feet 2 m from the axis when deployed (`deploy`/`retract`/`toggle` actions, deployed by its stage); the body is rebuilt (same pose and motion) after a dispatched action or stage changes the collider set.
- Heat (ADR 0023, plan 014; `thermal.ts`): every part has a skin temperature (`PartState.temperature`, K, snapshot `PartSnapshot.temperature`). In flight, a part in an airflow receives `k·√(ρ/r_n)·v³` (Sutton-Graves, `k = 1.74e-4`, `r_n` = cylinder radius / half the narrower box side) over the area the flow hits (the drag model's projected areas weighted by `|v_axis|/|v|`; an attached end face is shielded). Modules with `absorbHeat` (the stock heat shield) carry part of that power away first. The skin (3 mm of aluminium, 7 290 J/(m²·K) per surface area) warms and radiates `ε·σ·A·(T⁴ − 288.15⁴)` with ε 0.8, integrated by implicit Euler (stable for any step, so rails vessels cool in 10 s chunks too). A part above `PartDefinition.maxTemperature` (default 2000 K since plan 212; the stock pod 2400 K, the heat shield 3300 K, the EVA suit and flag their own) after the step is cut off and destroyed: `part:damaged { cause: 'overheat', outcome: 'destroyed', temperature }`. The world rule `stock.reentry-heating` (0–1.2, default 1; plan 212, ADR 0204 point 4) scales the convective input only, so at 0 parts cool and never heat. Not modelled: conduction between parts, wake, convective cooling, heating on rails (debris on rails is still removed at the atmosphere top, ADR 0021).
- Atmosphere: `p = p0·exp(−h/H)` below the atmosphere height; the air temperature `T(h)` follows the body's `temperatureCurve` (288.15 K without one; plan 212, ADR 0204), `ρ = p / (R·T)` with `R = 287.05`, and the speed of sound `a = √(γ·R·T)`. The stock home and Sol's Earth use the 1976 standard atmosphere's layers (`STANDARD_ATMOSPHERE_TEMPERATURE`; the rescaled Earth shrinks them with its air): 340 m/s at sea level, 295 m/s at 11 km. Drag per part and per part-frame axis `−½ρC_d A_i |v_i| v_i`, `C_d = 0.3` unless the part sets `dragCoefficient` (the nose cone: 0.12), times the transonic factor of the part's Mach number (`machDragFactor`: 1 to Mach 0.8, 2.5 at 1.05, 2.2 at 1.3, 1.6 from Mach 2; one global curve). `Ambient` carries `temperature` and `speedOfSound`; the vessel snapshot `mach` (the root's airspeed) and `hottest` (the part nearest its limit, above half of it), and `PartSnapshot.maxTemperature` the limit. Lift comes only from modules (`stock.fin`, ADR 0035): there is no lift on bodies.

## Water and buoyancy (plan 067, ADR 0182)

`packages/sim/src/water.ts`. A terrain field may answer `waterAt(direction)`. The hills field does: the sea is where the warped map elevation is under `SEA_LEVEL`, plus the lakes. The water plane is the reference sphere, where the height function already puts both.

- **Seabed.** Over water, a vessel's ground tile is the seabed, `WATER_DEPTH` (30 m) under the plane, radial.
- **Forces.** Each step, a flight vessel within 200 m of the plane over water gets buoyancy and water drag on 6 slices per part. Each slice holds a sixth of the part's shape volume and is wet by `clamp(0.5 + depth / extent)`, where the extent is the slice's vertical size for the part's tilt. Buoyancy is `ρ g V f` up, and drag is `−f ρ V (0.8 + 0.5 |v|) v`, both at the slice, so shape rights or tips the vessel.
- **Wet counts as landed.** A vessel with any wet slice is `landed` after the step, so it can come to rest, go to surface rails, warp and be recovered.
- **Impacts.** A part that gets wet this step, from dry, is judged by the ground damage rule at half its entry speed (`WATER_IMPACT_FACTOR`).
- **Splashed.** A landed vessel over water (`waterUnder`) is `splashed` for science.
- **No water by default.** Worlds without a terrain field have no water.

## Staging, splitting, resources

- `stage` runs `onStage` on the modules of `stages[nextStage]` and advances the counter. A module may call `ctx.vessel.detach(node, impulse)` (the stock decoupler does); after the hooks the sim cuts that attachment and splits the vessel (in flight: the one body is removed and one body per side is created, each side with the mass-weighted velocity of its parts and the old angular velocity, so momentum and angular momentum are conserved; the order is kept side first, then the new side): the side with a control source keeps the vessel id (the side with the old root if both or neither has one), the other becomes a new vessel (`<name> (debris)`, throttle 0, no stages), and the halves get equal and opposite momentum `impulse` along the node direction (turned by the part's yaw). `detach(node)` cuts every attachment on the node (the reserved `surface` node hosts several). When one stage's hooks queue several detaches (the radial decouplers of four boosters), the cuts are applied as if simultaneous: each impulse is worked out against the vessel as it was before any of them, so boosters leave with equal speeds and the recoils add on the core (`processPending`); one detach is the plain split above.
- Resources are generic (`ResourceStore` modules, `flowMode`, `crossfeed`, ADR 0015): `none` only the requesting part itself (plan 210), `vessel` every store on the vessel, `stack` breadth-first from the requesting part never entering a part with `crossfeed: false`, nearest store first; a **fuel line** (`connector: { feeds: true }`, ADR 0071) that ends on a visited part adds the part it hangs on (even with `crossfeed: false`) and what that reaches ahead of the visited part, one way, so a core engine drains its boosters first (`reachableParts` in `resources.ts`; `apps/web/src/lib/delta-v.ts` mirrors it). Shortfall is the module's business (stock engines flame out and emit `stock:engine-flameout`).
- **Flow locks, transfers and rates** (plan 213, ADR 0220): a store's `locked(config, state, resource)` hook takes it out of every flow search and transfer; `set-flow-lock` sets it through `setLocked`. A `transfer` is a job on `VesselState.transfers` that `runTransfers` (`transfer.ts`) moves on by `rate × dt` in flight and rails steps, ending when the sources are empty or the targets full; flow mode `none` is refused ("Solid fuel cannot be transferred"). Rates are measured: every 0.1 s `updateRates` compares each part's amounts with its last sample (`PartState.rateBase`, `rateAt`) and keeps the net flow per resource in `PartState.rates`, smoothed over 1 s; only vessels in flight or running a transfer are measured. `PartSnapshot.resources` and `VesselSnapshot.resources` carry amount, capacity, rate, time to empty and lock.
- Hooks get `ModuleContext` with `vessel: VesselApi` (`plugin-system.md`).

## Data items (plan 083, ADR 0172)

A data item (`DataItem`: `id`, `kind`, `bits`, `value`, `time`, optional `source`, `subject`, `meta`) lives in the state of a module that declares `dataStorage: { capacity(config) }`. Its state is `{ items, next }`, so items are saved, resumed and staged with their part like any module state, and the save format does not change. `packages/sim/src/data.ts` is the only code that reads or writes them. `ctx.vessel.data.store(item)` puts the item on the first storage of the vessel (part order, then module order) with room, gives it the id `<part entity>:<next>`, and emits `data:stored`. With no room it drops the incoming item and emits `data:dropped` (`reason: 'full'`). Commands `move-data` (to the storage of another part of the same vessel, if it has room) and `delete-data` refuse unknown items, parts without storage and full targets. `VesselSnapshot.data` is `{ used, capacity, items }` for a vessel with storage; the stock storage module's snapshot lists its items. Stock: `stock.data-storage` on the `stock.data-drive` part (64 Mbit, 0.4 m), and kinds telemetry, voice, science, image and bulk (priorities 0 to 4). `dataValueAt(kind, item, t)` applies a kind's `valueCurve`.

## Part actions and action groups (plan 110, ADR 0174)

`packages/sim/src/actions.ts` reads every module's `describe(config, state).actions` on a vessel, in part, module and descriptor order. `action-group { vessel, group, value? }` wakes a vessel on rails like `action` does. It then calls the action of every enabled descriptor of the group, or of the vessel's custom group `custom.<slot>`, in the same dispatch, and applies `processPending` and the colliders once. Without a `value`, toggles go on unless the group is already all on. A descriptor of another kind skips a value it cannot take, and the command is refused when nothing applies. Custom groups come from the design's optional `groups` (`{ slot 1..10, label, members: [{ part, module, action }] }`, any `formatVersion`; `resolveVesselDesign` checks slots, parts and modules). They are kept on `VesselState.groups` as part entities; debris gets none, and a member on a part that left the vessel is skipped. Vessels in flight carry `VesselSnapshot.actions`: `groups` (`{ id, state, parts }`, registered groups by `order`, then custom groups) and `states` (`[part, module, action, value, enabled]`). A 100-part vessel is about 4.6 kB.

## Objectives (plan 098, ADR 0175)

`packages/sim/src/objectives.ts`. `objective-start { source: { kind, id }, vessel? }` checks the contract or mission, its prerequisites (completed sources) and that it is not already active, then adds an instance `o<n>` (with `deadline` = start + `deadline` for a contract) to `SimCore.objectives.state`. Instances are evaluated at the end of each flight step and each rails chunk when a current leaf listens to `'step'` or a listened event marked them during the step, and on each `world:tick` when a current leaf listens to `'tick'`. A passed deadline fails an instance. The view holds the bound vessel or every vessel: body, mode, landed (also on surface rails), altitude, and periapsis and apoapsis from the same conic the snapshot reports. On completion or failure the instance moves to `finished`, its reward or penalty is recorded in the ledger (`cause` = the source id) when the economy is on, and `objective:completed` or `objective:failed` is emitted. `Snapshot.objectives` lists every instance with per-leaf status and progress. `SimSave.objectives` (optional in format 5) is written once anything was started.
## Procedural contracts (plan 099, ADR 0186)

`packages/sim/src/contracts.ts`. `SimCore.contracts` (`SimSave.contracts`, optional, written once the generator has drawn) holds the offers, the accepted generated contracts, the declined keys' cooldowns, the id counter and the `contracts` stream state.

- **The generator** runs on each world tick after the economy, with the economy on and `stock.contracts` on. Expired offers (10 days) and cooldowns go first. Then, while there are fewer than 5 offers, it makes at most one: a weighted pick among the templates whose reputation gate passes and that are under their `maxOffers`. The template's `generate` gets its draws from the stream. The offer is dropped when its key is already offered, active or cooling down, or when its tree names an unregistered objective.
- **The commands:**
  - `contract-accept` checks the `mission-control` slots of the primary site (none = no limit), pays the advance (cause `contract.advance`) and starts an objective instance with source `{ kind: 'contract', id: 'gen.<n>' }` and `since`, the highest vessel id then. `definitionOf` resolves `gen.*` ids from the contract state. `viewFor` keeps only vessels with a higher id.
  - `contract-decline` sets the cooldown.
  - `contract-cancel` fails the instance with `cancelled`, and its penalty is booked.
- **Plan 231 (ADR 0231):**
  - Templates get `ctx.milestones`, the world's firsts so far, and the stock rescue, satellite, station and docking templates wait for theirs.
  - A blueprint's `spawn` is made on accept: the design on rails in a circular orbit at `altitude`, and with `member` a new crew member stranded in its first seat (`strandMember`: free, past the roster cap). It is kept on the offer as `spawned`.
  - The objective view's vessels carry:
    - `inclination`;
    - `seats` and `crew`;
    - `antenna` (a module with an antenna hook);
    - `power` (a module whose power rate is positive);
    - `ports`;
    - `docked` (the vessel has dock records).
  - `viewFor` keeps a vessel from before the instance when a vessel newer than `since` docked to it.
  - `ObjectiveView.rescues` lists the instance's stranded members with their status. `stock.rescue` is done when they are `available` again (recovered), and failed when one is lost.
- **`Snapshot.contracts`** carries `enabled`, `slots`, `used`, the offers with `value`, and the accepted ones with their instance, status and deadline.

## Strategies (plan 101, ADR 0187)

`packages/sim/src/strategies.ts`. `SimCore.strategies` (`SimSave.strategies`, optional, written once anything was activated) holds the active strategies and the cooldowns.

- **`multiplierOf(core, key)`** is the product of the active strategies' factors on a key, clamped to the key's bounds (`STRATEGY_KEYS`). It is 1 with the economy off. The keys act in these places:
  - `launch-cost` in `launchCost`;
  - `recovery` in `creditRecovery`;
  - `science` in the science booked by `creditScience` and in rewards;
  - `reputation` on positive reputation rewards;

- **Commands:** `strategy-activate` checks the agency type, an active duplicate, the cooldown and the `admin` slots. `strategy-end` starts the cooldown.
- **`Snapshot.strategies`** (economy on) lists the strategies on offer with each key's bounds, and the current multipliers.

## Rival agencies (plan 126, ADR 0190)

`packages/sim/src/agencies.ts`. `SimCore.agencies` (`SimSave.agencies`, optional) holds each running agency's funds, reputation, next mission, ready day, stream state and objects, plus the rentals and the last 50 news items.

- **The daily step:** `agenciesTick` runs on each world tick after the economy, for the first `stock.agency-count` registered agencies. Each one:
  - gains `monthly / 30`;
  - retires objects at the end of their life;
  - fails relays at `0.2 × risk / lifeDays` per day, with news and a reactive contract offer (template `agency.<id>`) in the contract offers;
  - launches its next mission when ready and paid for. The success roll is `success × (1 − 0.3 × risk)`, and the next one is due after `prepDays × (1.5 − aggressiveness)` days.
- **Objects:** a success places a probe core and dish on a circular orbit of home (phase from the stream) on rails, with `VesselState.owner`. At most 2 per agency; the oldest is deorbited.
- **Passive:** owned objects skip the per-chunk update hooks, heat, rebasing, SOI checks, debris and milestones. Unrented, they are not on the comms network.
- **Commands:**
  - every command naming an owned vessel is refused (`owned by <name>`), except `relay-rent`, `relay-end-rent` and `comms-inspect`;
  - `relay-rent` adds a rental, which books `agency.rent` daily and puts the relay on the network.
- **`Snapshot.agencies`** carries the agencies and the news, newest first; `VesselSnapshot.owner` names an object's agency.
- **ECS query:** `world.query` reuses its answer until an entity joins or leaves a queried component. Rails chunks of 10 s ask for the vessels many times each.

## Crew (plan 106, ADR 0176)
`packages/sim/src/crew.ts`. `SimCore.crew` (`SimSave.crew`, optional in format 5, written once anyone is hired) holds the roster, the id counter and the `crew` stream state. `crew-hire { profession }` draws a name and traits from that stream and books the recruit fee (20 days of the base salary) when economy and salaries are on; `crew-dismiss { member }` lets an available member go (they leave the roster, `crew:dismissed`; a seated, missing or lost member is refused; contract `cp/f3-contract-crew-dismiss`, API 0.1.59). `load-vessel { crew: [{ member, part }] }` seats available members within `crewCapacity`, and `crew-transfer` moves one between parts of a vessel. A member's location is the part entity, so staging carries them along. After each step, everyone aboard collects places: `flyby:<body>` outside home's sphere, `orbit:<body>` on a closed orbit whose periapsis clears the atmosphere, `landed:<body>` on a body other than home. At `recover-vessel`, with `stock.crew-experience` on, each new place books `kind × body` XP (flyby 1, orbit 1.5, landed 2.3; other bodies ×2), and the member is available again. Any other `destroyVessel` applies `stock.crew-death`: `permanent` → lost, `return` → missing until `stock.crew-return-days` days later (checked on world ticks), `off` → available. On each world tick, with economy and salaries on, salaries are one `crew.salaries` ledger entry. `Snapshot.crew` lists the roster, and `VesselSnapshot.crew` who sits where, with ability factors. The command-source rule of ADR 0109 (crew needed for control) is plan 114's.

**Crew simulation (plan 107, ADR 0181).** `packages/sim/src/life.ts`. `updateCrewLife(core, t0, flight)` runs after every flight step and rails chunk, for each vessel with crew aboard:

- **Life support** (`stock.life-support`). `simple` draws `stock.supplies`, and `full` draws oxygen, water and food, each at 1 unit per crew member per root day. `full` also needs scrubbing: modules with a `scrubber` hook serve people while the vessel has electric charge. The interval is integrated piecewise linearly and cut at each run-out (`amount / rate`), so a run-out is dated exactly at any warp. A run-out (or a scrubber shortfall: `co2`) adds `{ resource, since }` to each member's `shortages` and emits `crew:shortage` with that time. Resupply clears it (`crew:resupplied`). Past the grace (oxygen and CO2 1 800 s; water and supplies 3 days; food 10 days), the death rule applies to that member (`loseMember`).
- **Morale** (`stock.crew-morale`) relaxes towards `1 − 0.01 × days aboard − 0.3 × max(0, crowding − 0.5) − 0.4 × shortage`, with a time constant of one day.
- **Fatigue** (`stock.crew-rest`) rises 1.5 per day in flight mode and falls 3 per day on rails.
- **Exposure** (`stock.crew-exposure`). The dose grows at 1e-5 mSv/s in the home sphere outside the air, and at 5e-5 beyond it. In flight, the proper acceleration over `6 g × gTolerance` builds a stress that blacks a member out for 8 s past 3 g·s (`crew:g-loc`).

`VesselSnapshot.crew` carries the condition and the performance `(0.6 + 0.4 m)(1 − 0.4 f)`, which scales the reported abilities. `VesselSnapshot.lifeSupport` gives the time left per consumable. Recovery and loss end a flight's condition; the dose stays. The member fields save in `SimSave.crew`.

## EVA (plan 109, ADR 0120)

`packages/sim/src/eva.ts`. The suit is a vessel of one part (the registered part with a seat and `walk`; stock `stock.eva-suit`). `crew-eva { vessel, member }` wakes the vessel and spawns the suit east of it, past its farthest part (standing on the ground when the vessel stands, else at its velocity), then moves the member into the suit; the place `eva:<body>` and the `eva` milestone follow. `crew-board { suit, vessel }` needs the same sphere, 50 m and 2 m/s; it seats the member, runs the suit's `onRecover` hooks with their credit going into the vessel's sample locker (`VesselState.samples`, credited by `recoverScience`), and removes the suit as recovered. `crew-walk { vessel, heading, speed }` stores `VesselState.walk`; before each step `stepWalking` keeps a landed walker upright (its spin is the ground's) and gives it the ground speed it walks at, keeping the vertical motion. `plant-flag { vessel }` spawns the registered part with a `keep` module beside a standing suit; a kept vessel is never reaped as debris and rests on surface rails like a controlled one. The jetpack is the stock engine on `stock.eva-propellant`.

**EVA v2 (plan 225, ADR 0209).** Additions to `eva.ts`:

- **Hatches.** A part's `hatch { pos, dir }` is where crew step out. `crew-eva` first checks a 1.2 m segment out of the seat part's hatch against the other parts' boxes in design space, and refuses with "Hatch blocked by <title>". The suit then appears 1 m out of the hatch. A part without a hatch keeps the old east placement.
- **Boarding.** `crew-board` needs the suit within 2 m of a hatch's exit point, or latched to a ladder of that vessel. The rule `stock.eva-board-assist` (on in Sandbox only) keeps the old 50 m range instead.
- **Suit propellant.** The suit's `walk.propellant` is kept per member (`CrewMember.suitGas`). Boarding tops the suit up from the vessel's own stock with `withdrawFrom` over the vessel's parts; the next EVA starts the suit with that amount (full the first time).
- **Ladders.** A part's `ladder { from, to, out }` is a segment a suit hangs on, 0.45 m out. `crew-grab { suit }` latches to the nearest one within 1 m (`VesselState.latch { vessel, part, s, rate }`); `crew-grab { suit, release: true }` lets go; `crew-climb { suit, rate }` moves `s` at 0.6 m/s × rate. Before each step `stepLatch` sets the suit's pose and velocity to the ladder point's on the vessel's body, as if rigid, so it keeps its offset while the vessel turns.
- **Moving.** `crew-jump { suit }` adds 2.5 m/s up at the next step while standing. `walk.run` raises the `crew-walk` limit.
- **The jetpack** is the `stock.jetpack` module: 270 N along `attitude.translate`, Isp 200 s on 20 kg of cold gas, about 390 m/s. The page turns the keys, relative to the camera (`Renderer.viewDirection()`), into the suit's frame. Suits in older saves keep their engine module.

## Site templates and founding sites (plan 092, ADR 0177)

`resolveSiteTemplate(template, { seed, radius })` (`packages/core/src/site-templates.ts`) finds a template's spot on a world. It reads the biome map of the terrain seed without zones, at the warped coordinates the terrain reads. Land is ≥ `landFull` and sea is < `landStart`. A spot counts when it and eight points 8 km around it are land. The search is a coarse grid of 1° × 2° in the |latitude| band, then a 0.1° refinement around the best spot by the score (closeness to the band's middle, then to longitude 0). When nothing meets every criterion, `island`, `seaEast`, `inland` and `minElevation` are dropped in that order and reported. `siteConsequences` gives the rotation boost `ω R cos φ`, the lowest inclination `|φ|`, the downrange east (sea, land or mixed to 1 000 km) and the nearest other site. Create World writes a template's spot as the world's first site (`space-center`, the Legacy pad and layout). `found-site { id, name, latitude, longitude, body? }` (`packages/sim/src/buildings.ts`) appends a `base` with the starter pad after the Legacy site. It is refused beyond 8 sites on a body or when the zones would overlap. Because zones are built at `createSim`, a `site` placement there is refused until the world is loaded again.

## Branch space centers (plan 236, ADR 0229)

`found-branch` (`packages/sim/src/buildings.ts`) founds a site of kind `branch` on the home body with the site rules of `found-site` (`siteRefusal`: a free id, at most eight zones, no overlap). The founding cost and time are the level 1 of the building that provides `branch-hq` (`branchHqOf`; stock's `stock.branch-hq`, 250 000 funds, 20 days), paid with the economy on; the branch starts with that HQ under construction at `BRANCH_HQ_CELL`. `canPlace` refuses every other kind at a branch until its HQ works (`hqReady`, code `hq`) and refuses placing a `branch-hq` building by hand. A branch is a ground station only while it has a working `comms-node` building (`stationsOf`). A vessel launches from any site with `{ kind: 'site', site, at: { east, north } }`, so the fuel and launch charge come from that site's storage; a site founded in the run still takes vessels only after the world is loaded again, and the web reloads right after founding. The debug cheat `instant-construction`, turned on, also finishes work in progress (`finishConstruction`).

## Science (plan 103, ADR 0178)

`packages/sim/src/science.ts`. `ctx.vessel.situation()` classifies the vessel with the registered situations (lowest `order` first) over `{ landed, splashed, altitude, atmosphereHeight, flyingHigh, spaceHigh }`. Landed includes surface rails. Splashed means landed on terrain below sea level, on a body with an atmosphere. The thresholds come from the body's `science` field, through `bodyScience`. The result is cached per vessel for 1 s of sim time, and recomputed at once after an SOI or landed change. The snapshot classifies fresh, without touching the cache, so a UI that asks changes nothing modules see. `ctx.vessel.science.result(experiment)` fixes the value of a result when it is made: `min(cap − produced, base × multiplier × r^count)`. It adds to the subject `<experiment>@<body>:<situation>:global` in `SimCore.science.subjects` and emits `science:result`. `transmit-data { vessel, item }` credits a science item (one with a known `subject`) at `value × meta.transmitFactor`, then deletes it. `recover-vessel` credits every science item aboard at full value, then calls each module's `onRecover` (a held sample is credited there). Credit adds to the subject's `credited` and emits `science:credited`. When `stock.tech-tree` is on, it also becomes a `science` ledger entry × `stock.science-multiplier` (`cause` `science.<experiment>`, `ref` the subject). `Snapshot.science` lists the subjects. `VesselSnapshot.science` gives the situation and each module's `describe().experiment`. `SimSave.science` (optional in format 5) is written once a subject exists. Stock `stock.experiment` modules are READY, RUNNING, PAUSED or INVALID. They draw `power` EC/s while running, and work on rails too (`updateOnRails`).

**Regions and dossiers (plan 104, ADR 0180).** A body's `regions` are the biomes of the world's planet map, seeded cells, or latitude bands. `regionAt(body, direction, world)` (core) reads them. For biomes it uses the map and warped coordinates the ground shader draws with. A result in a `regional` situation takes the region under the vessel (`regionUnder`, body-fixed at the time of the result), and other situations take `global`. The value uses `body multiplier × region multiplier`. `VesselSnapshot.science.region` shows the region now. Dossiers are not sim state: `dossierOf(body, subjects, entries)` derives them from the subjects (the web parses `Snapshot.science` ids with `parseSubjectId`). An entry unlocks once a subject on the body with a result matches its `unlock` situations and experiments.

**Discovery science (plan 129, ADR 0192).** `packages/sim/src/discovery.ts`. It runs only with `stock.science-depth` `discovery`; with `classic` every function returns at once and classic points are credited the same in both depths.

- **Facts.** Every body that is not a star has one of each registered fact kind, from `factValue(seed, body, kind)` (core). It is drawn on its own stream (`discovery.fact:<body>:<kind>`), is 0 when absent, and is never saved.
- **Measurements.** `makeResult` of a data experiment listed in a kind's `instruments` returns `meta['discovery:<kind>']`. Its value is the truth plus `resolution × N(0, 1)`, floored at 0, from the `discovery` stream (`SimCore.discovery.rng`). The stock experiment module copies the meta onto the item.
- **Datasets.** `transmit-data`, a comms delivery and `recover-vessel` call `intakeData`: each measurement on a credited item becomes a raw dataset `{ id, body, fact, level, value, sigma }`.
- **Lab.** `discovery-process { dataset }` starts the next level. It is refused when the dataset is already derived or in the lab, or when the primary site's `lab` capacity is in use (null means no limit). `discoveryTick` finishes it on the first world tick at or after `DISCOVERY_PROCESS_DAYS` (calibrated 2, derived 5). The error then scales by `LEVEL_ERROR` (1, 0.5, 0.25), exactly, without a new draw.
- **Claims.** `discovery-claim { body, fact, value, confidence }` takes a confidence in [0.5, 1], one open claim per fact. It is reviewed on the first tick at or after `DISCOVERY_REVIEW_DAYS` (3) days.
  - It is accepted when within the kind's `tolerance`.
  - The reputation change is `reviewScore`: `20 × (1 − 4(o − c)²)`, and a quarter of a positive score when the fact's priority is already taken.
  - The change is booked as `discovery.review` with the economy on, and `discovery:reviewed` is emitted.
- **Snapshot and save.** `Snapshot.discovery` holds the fact views (never the truth of an open fact), the datasets, the claims and the lab slots. `SimSave.discovery` (optional) holds the stream, the datasets and the claims once anything happened.

## Comms tier 1 (plan 114, ADR 0179)

`packages/sim/src/comms.ts`. Ground stations are every world site and every registered `defineGroundStation`, 10 m above the ground and turning with their body. A site's range comes from the tier of its active `comms-node` buildings (2e9, 5e10 or 2.5e11 m; tier 1 without one, except a branch, which is no station without one; plan 236). A vessel's range is its strongest enabled antenna (a module with an `antenna` hook). It links directly to the nearest station, or vessel with a crewed command part and an antenna, when four checks pass:

- the distance is under `√(range_a × range_b) × stock.comms-scale`;
- the segment misses every body sphere;
- no terrain sample is above the segment where it runs low over a body with terrain;
- the vessel's plasma blackout (core's `blackoutLevelFromFlux` of the stagnation flux at the vessel) is under the badge level.

The first failing check is the reason. `updateNetwork` runs after each step and rails chunk, once 1 s has passed or when the network is dirty (staging, an SOI change, a vessel created or removed, an action, a rule change, a building or site change). Rails chunks are sampled at most 10 s apart. A change on a rails vessel is dated by bisection on its rails position to 0.01 s, and in flight at the sample. It emits `comms:link-up`, `comms:link-down` (with `time`) and `comms:control-changed`.

A probe is a vessel whose control sources all sit on parts without seats. A probe without a link gets the control state of `stock.control-without-signal`: `partial` refuses `throttle` and `attitude`, `none` also `sas`, `stage`, `action` (except antenna actions) and `action-group`, with the reason. Crewed command parts count as crewed without crew until plan 108. Links are derived and never saved. The first update after creation or resume is silent. `Snapshot.network` lists the stations (system-relative positions) and each vessel's link; it is computed fresh, without storing, while the network is dirty. `ctx.vessel.signal()` gives modules the last state. With `stock.comms` off there is no network.

## Comms tier 2 (plan 116, ADR 0185)

The tier-1 rule still decides whether a vessel is linked. At each network update's last sample, a linked vessel gets a downlink budget to its endpoint (`bestBudget`):

- **The pair:** every enabled, working antenna with a registered band (`registries.bands`) transmits. A station receives on every band with its dish: 10, 34 or 70 m by site tier, or the station's `aperture`. A vessel endpoint receives with its antennas on the same band. The pair with the highest margin wins.
- **The budget:** core's `linkBudget` (Friis). The distance is divided by `stock.comms-scale`. The margin is taken at 1 kbit/s, and the rate is a decade step from 1 kbit/s to 1 Gbit/s, one per 10 dB of margin (0 below: commands only).
- **Without a common band** the budget is null: the link stands, and the rate is null.

`Snapshot.network.vessels` carries `rate` and `margin`, and `ctx.vessel.signal().rate` gives the rate. The command `comms-inspect { vessel | null }` is view state, never saved. Its vessel's full budget is in `Snapshot.network.inspector`.


## Comms tier 3 (plan 117, ADR 0188)

`routeNetwork` in `packages/sim/src/comms.ts` replaces the direct link at every network sample. The tier-1 `linkOf` remains for the bisection and for the reason a vessel without a route gives.

- **Vertices:** the stations, and every vessel with a working antenna and no blackout. Stations and vessels with a crewed command part are control points.
- **Edges:** pairs that pass the tier-1 range, line-of-sight and terrain checks. A cheap squared-distance reject comes first.
  - A dish whose module state has a `target` (`antenna-point`) only reaches what lies within half its beam (`beamWidthOf`) of that target's direction.
  - A capacity is the tier-2 rate from the far end. It comes from a reference margin per pair of antenna sets, less 20·log10 of the distance, so there is one budget per kind of pair.
- **Routes:**
  - **Auto** is the vessel's branch of a multi-source widest-path tree from the control points (O(V²)). Ties go to fewer hops, then shorter, then the ids.
  - **Manual** follows `SaveComms.routes`' pinned hops. It fails as `route broken at <id>`.
  - **Policy** asks a registered `choose` among the best route through each neighbour.
- **Capacity sharing:** three proportional rounds over the used edges give each route its rate.
- **Network vessels** carry the first hop as `to`, plus `route`, `latency` (length / c), `rate` (shared) and `mode`.

**Signal delay** (`packages/sim/src/delay.ts`):
- `dispatch(core, command, source)` queues `throttle`, `attitude`, `sas`, `stage`, `action` and `action-group` for a linked probe under `stock.signal-delay` `enforced` (and `flight-computer` unless `source` is `script`). The delay is the route's latency, and the command returns `{ ok, queued: at }`.
- The queue (`SimCore.commsState.queue`, `{ at, seq, command }`) drains at the start of each flight step and rails chunk, through `dispatch(…, 'queued')`, so every check runs again.
- **Save format 7:** `SimSave.comms = { seq, routes, queue }`. Migration 6 → 7 adds an empty one; `save-v6.json` is the frozen fixture.


## Comms tier 4 (plan 119, ADR 0189)

`packages/sim/src/transmission.ts`.

- **Queueing:** with comms on, `transmit-data` moves an item out of its storage into `SimCore.commsState.transmissions` (`{ seq, holder, origin, item, sent, hops }`, saved). With comms off it credits at once. `transmission-cancel` restores the item with its id.
- **Sending:** at each network sample, `stepTransmissions` spends the time since the last sample on each holder's queue, in kind priority order (`stock.command` is −1) and then `seq`.
  - **A holder with a route** sends at its shared rate (command items move at 1 kbit/s even over a commands-only link). It delivers with `comms:data-delivered { vessel: origin, item, kind, bits, time }` and credits science at `dataValueAt × transmitFactor`.
  - **A holder without a route** hands its head item to a neighbour with free data storage whose next direct contact comes earlier (store-and-forward, at most 8 hops).
- **Rates:** budgets are computed at every sample while anything is queued, so rails chunks transmit in the background over their sampled windows.
- **Next contact:** `nextDirectContact` scans the tier-1 rule every 60 s for a home day, cached 60 s per holder.
- **Snapshot:** `Snapshot.network.queues` lists the holders, with `nextContact`, `custody` and each item's `sent` and `eta`.
- **Recovery** credits queued science at full value.
- **Save format 8:** `comms.transmissions`. Migration 7 → 8 adds an empty list; `save-v7.json` is the frozen fixture.


## Comms tier 5 (plan 120, ADR 0191)

- **Channels:** a band has `channels` (default 4), and the stock antenna module's state holds `channel` and `encrypted`, set by its `setChannel` and `setEncrypted` actions. `bestBudget` keeps the transmitting antenna's channel and encryption on the budget.
- **Interference:** after routing, with `stock.comms-interference` on, every first hop loses 3 dB (capped at 12) for each other routed first hop on the same band and channel whose transmitter has an edge to its receiver. Encryption then sends at 0.8 times the rate, and the route's width is the smaller one before capacity sharing.
- **Licences:** `licence-buy { band, channel }` books the band's `licence` price (cause `comms.licence`) and adds to `SimSave.comms.licences`. Channel 0 is always licensed. `transmit-data` is refused on an unlicensed channel; links and commands are not.
- **Snapshot:** network vessels carry `channel`, `encrypted` and `interference`, and `Snapshot.network.licences` lists the licences.

## Comms tier 6 (plan 121, ADR 0193)

`packages/sim/src/comms.ts` and `broadcast.ts`.

- **Suit radios:** a vessel whose enabled antennas are all `suit: true` is a suit node.
  - It links only to a crewed vessel that is not a suit. It never links to a station, a probe or another suit.
  - It is in range under its own radio's rating × the world's comms scale, not the geometric mean.
  - The edge's budget uses the suit's antennas at both ends.
  - It is no control point, and nobody routes through it.
  - Its rating is multiplied by the best `radio` ability aboard.
  - An edge with a suit samples the terrain every `SUIT_SAMPLE_SPACING` (1 m), at least 16 times.
  - A cut suit link has the tier 1 reason (`blocked by terrain`, `out of range`); control stays full, because the suit is crewed.
- **Broadcasts:** `comms-broadcast { milestone }` books `BROADCAST_FACTOR × milestoneReputation` (cause `comms.broadcast`, ref the milestone). It is refused, with a reason:
  - after `BROADCAST_WINDOW` (3 600 s);
  - a second time;
  - with comms off;
  - when the milestone's vessel has no rate of `BROADCAST_RATE` (10⁵ bit/s) to the ground. The rate follows a suit on through its relay, and the lowest along the chain counts.
- **Snapshot and save:** `Snapshot.network.broadcasts` lists the open ones with the rate now. `SimSave.comms.broadcasts` (optional) keeps the done ones.

## Power (plan 208, ADR 0214)

- **Resources:** `stock.monopropellant` (4 kg/u, `vessel` flow), `stock.solid-fuel` (7.5 kg/u, `none` flow) and `stock.cold-gas` (1 kg/u), the renamed EVA propellant. Save format 9: migration 8 → 9 renames `stock.eva-propellant` everywhere in the save (`renameId`).
- **Sunlight:** `VesselApi.sunExposure(dt, factor)` (`packages/sim/src/sunlight.ts`) averages `factor(direction) × flux`. The direction is the star in the part frame. The flux is inverse square relative to the home planet's orbit, and 0 inside a body's shadow cylinder. In flight it takes one sample; on rails it samples every 10 s along the rails path (at most 4 096 samples), with the frozen orientation. The stock panel modes are `flat` (cos to `normal`) and `track` (about the part's +Y); `deployable: false` makes a fixed panel. The RTG gives a constant 0.75 EC/s.
- **Control:** `ModuleDefinition.needs(config)` names the resource a control source runs on (a probe core with `drain`). `controlProblem` gives `no-source`, `no-crew` (plan 200, ADR 0216: a seat part is a source only with crew aboard, and the comms graph skips an empty one) or `no-power`; control commands are refused with that reason, and `VesselSnapshot.uncontrolled` carries it. `vessel:power-depleted` fires once when a vessel runs out (`power.ts`), and the web shows an "Out of power" toast and the "Uncontrolled" chip.
- **Transmission cost:** each bit sent costs the strongest antenna's `power` × `TRANSMIT_EC_PER_MBIT_PER_W` (0.2) EC per Mbit, drawn from the holder. A radio sends only what its charge pays for, so the queue pauses at 0 EC.
- **Budget:** `powerBudget(partIds, registries)` in core gives the net EC/s by day and by night, the capacity and the night reserve, from each module's `power(config)` descriptor.

## The pad and auto-crew (plan 200, ADR 0216)

- **Auto-crew:** `load-vessel` without a `crew` field calls `autoCrew` (`crew.ts`) when the vessel would be `no-crew`: the first available member takes the first seat of a crewed control part; with nobody available and `stock.economy` off, a pilot is hired first. `crew: []` keeps the vessel empty.
- **Liftoff:** `VesselState.launchedAt` is set by the first `stage` command, or at load for a vessel not placed on the surface; split pieces copy it, and the snapshot carries it. Before it the vessel is pre-launch. The web's 50 % launch throttle is sent with the first stage, so the vessel rests on the pad until then. The web reads pre-launch from the snapshot (no `launchedAt`, `nextStage` 0, within 200 m of the ground) and counts MET from `launchedAt`.

## Port targets, control parts and autopilots (plan 310, ADRs 0270 and 0271)

- A target that names a docking port resolves `target.position`/`velocity` from the own reference point (the control part's port face when the control part is a port, else the centre of mass) to that port's face, each with its own velocity (`target.ts`). The closest approach stays between centres of mass.
- `attitude` input is in the control part's axes; the sim turns it into the vessel's before storing it.
- SAS `direction` points the control nose along `sas.direction`. `hold` with an `attitude` holds the control part at that orientation.
- Engaged autopilots (`autopilot.ts`) step at their rate, once per fixed step, before the sim chooses a flight step or a rails chunk. A docking ends both vessels' autopilots as `done`.

## RCS (plan 211, ADR 0217)

- `set-rcs` switches the vessel's RCS (`VesselState.rcs`, `VesselSnapshot.rcs`). `attitude.translate` (vessel axes: x right, y forward, z up) sets the translation; modules read `VesselApi.rcs` and `VesselApi.translateDemand` (part frame).
- Stock `stock.rcs` fires each nozzle at `clamp(dir · T + mix(R, lever × dir), 0, 1) × limiter`, burns `thrust / (Isp g0)` with the Isp by pressure, and reports `firing` and `dry`. While RCS is on it adds `Σ |lever × dir| × thrust / 2` to the SAS authority (`controlAuthority`).

## Fairings (plan 219, ADR 0224)

- Design parts' `settings` merge over the module config at `spawnVessel`. `ModuleDefinition.mass` adds to `partMass`. `shieldedParts` (`debris.ts`) finds the parts inside a closed `shell` profile; the drag pass skips them (no drag, no convective heat) and draws the shell's part as a cylinder of the shell (`shellShape`, Cd 0.12).
- `VesselApi.spawnDebris` queues a piece; `spawnQueuedDebris` (after `processPending`) spawns it at the source part's pose and velocity plus the push, in the same frame. Stock `stock.fairing` throws two `stock.fairing-panel`s off sideways, each half the shell's mass.

## Solid motors and launch clamps (plan 210, ADR 0219)

- `stock.engine` with `solid: true` ignores the throttle and cannot shut down; every engine has `limiter` (scales the mass flow), `gimbalLock` and `gimbalLimit`. Flow mode `none` reaches only the drawing part (`sources` in `resources.ts`), so a motor burns its own solid fuel.
- `ModuleDefinition.anchor(config, state)`: `holdAnchored` in `frames.ts` runs after the backend step and puts a vessel with an anchoring part (and a ground tile) back to its body-fixed pose (`VesselState.anchor`), moving with the ground. Stock `stock.launch-clamp` measures the ground under its tower with `VesselApi.groundClearance`, feeds 20 EC/s and detaches on staging; the clamp vessel stays held.
- Save format 10 turns a flying liquid BST-1 into the solid one at the same fill.

## Docking (plan 222, ADR 0218)

- Port module hooks: `dock(config)` gives `{ size, node }`; `crossfeed(config, state)` closes the part to stack flow (`passesFlow` in `resources.ts`). Stock `stock.docking-port` in three sizes, with Undock (detach the face node, 150 N·s) and Crossfeed.
- `docking.ts`: `wakePortNeighbours` (after the queue: an on-rails port vessel within 50 m of a flight one joins flight), `pullPorts` (before the step: aligned equal-size free faces within 5 m and 15° pull at 0.15 m/s² below 0.3 m/s closing; port vessels within 50 m stay active), `capturePorts` (after the splits: within 0.15 m under 0.5 m/s they merge; faster they bounce for 10 s).
- Merge: the keeper (controlled, heavier, lower id) takes the other's parts in its frame and indices, one body from the joint momentum, and a `DockRecord` in `VesselState.docks`. Undock's split calls `restoreUndocked`, which gives both sides their names, designs, indices and stages back. Events `vessel:docked`, `vessel:undocked`; milestones `dock`, `undock`.
- Tethers (plan 313, ADR 0272): a winch's rope is the sim's, not a physics joint (`tethers.ts`). Before each step a taut, separating rope gets equal and opposite pulls at its anchors (the impulse that stops the separation, plus up to 3 m/s of overshoot correction); the pull smoothed over 0.1 s is the tension, and above the strength the rope snaps. The pair is `PartState.tether` on the winch part (saved); an armed winch wakes socket vessels in reach, and tied vessels stay in flight.
- Built docked (plan 356, ADR 0300): an attachment that joins two ports' dock nodes is marked `docked` when the vessel spawns (`dockBuiltPairs`), so Undock works on a payload built face to face in the Hangar. Any split between two ports releases both (`docked: false`, `UNDOCK_COOLDOWN`) and sets `PartState.portLeft`: the two neither pull nor capture each other again until their faces have been beyond `MAGNET_RANGE`, so a payload set free drifts away. `stageUndock` (a build setting of `stock.docking-port`) undocks on the port's stage.
- `TargetRef.part` targets a port; `TargetSnapshot.port` is the alignment; `VesselSnapshot.ports` the port faces.

## Parachutes (plan 209, ADR 0203 point 4)

`mods/stock/src/parachute.ts`, module `stock.parachute`; parts `stock.parachute` (top, 0.625 m), `stock.radial-parachute` and `stock.drogue-chute`.

- **States:** `stowed` → `armed` (staging or Deploy) → `semi` once the static pressure reaches `minPressure` (atm; mains 0.04, drogue 0.02) → `full` below `deployHeight` above the ground (mains 1 000 m, drogue 2 500 m). Cut and torn are final (no repack yet). Disarm returns an armed chute to stowed; Force deploy opens it at once.
- **Safety:** from the airflow at the part, Risky from `riskySpeed` or `riskyQ`, Unsafe from `unsafeSpeed` or `unsafeQ` (mains 250 / 330 m/s, 50 / 80 kPa, above the about 44 kPa a capsule falls at, `q = m g / CdA` at terminal speed; a drogue about twice the speed). "When safe" (the default) waits while the air is Unsafe; an open canopy in Unsafe air tears (`stock:parachute-torn`). The module refreshes `safety` in its state every flight step, so the panel's text is the class it tears by.
- **Drag:** `½ ρ CdA |v| v` against the part's air velocity at its `anchor` (the top), with `CdA` ramping over `semiSeconds` (1 s) to `semiDragArea`, then over `fullSeconds` (3 s) to `fullDragArea`. A main of 480 m² brings a 1 t capsule down at about 6 m/s at sea level. The vessel hangs below the anchor.
- **Height above the ground:** `Ambient.height` (new, optional) is the altitude less the terrain under the part (`terrainBelow`), filled by the sim's hook API.
- **Snapshot and panel:** `status`, `mode`, `minPressure`, `deployHeight`, `opening`, `safety`, `canopy` (0 stowed, 0.3 semi, 1 full: the renderer's deploy flag, which may now be a number) and `open`. `ModuleInfo.readouts` (new) carries the status and the airflow as text for the part panel.
- **Events:** `stock:parachute-deployed { part, stage }` and `stock:parachute-torn { part, speed }`; the web makes toasts, a deploy sound and log lines of them.

## Range safety (plan 127, ADR 0155)

`packages/core/src/range-safety.ts` and `packages/sim/src/range.ts`; rule `stock.range-safety` (`cost` default in Career, `hard`, `off`). A site's safe fan (`safeFan`, cached per run in `SimCore.range.fans`) is every 5° azimuth whose track from 20 to 200 km is water (`TerrainField.waterAt`, plan 067) at 75 % of its 10 km samples and passes 50 km clear of other sites; a body without `waterAt` has none and is not judged. A `stage` command that fires a separator (a module whose `describe` has an unfinished `separator`) on a controlled vessel more than 100 m above the ground takes the vessel's state as the spent stage's: `conicImpact` follows the drag-free conic (the debris rails model) to the reference radius, the body turns for the flight time, and `dropProblem` names a site within 50 km or land. `hard` refuses the command with the reason; `cost` fires it and books `RANGE_PENALTIES` once through the ledger (cause `range-safety`, ref `<kind>:<vessel>`, funds times the cost multiplier, only with `stock.economy` on). A vessel loaded at a site is watched (`SimSave.range.pending`, optional in format 5) until it climbs through 2 km above the ground; the heading of its velocity over the turning ground is then compared with the site's fan (`azimuth` violation, booked under `cost` and `hard`). Each violation emits `range:violation { vessel, kind, site?, latitude?, longitude?, azimuth?, penalised }`. `Snapshot.range` (absent when off) carries the mode, the fan of the latest watched ascent's site (else the primary site) and, per controlled vessel in flight, the predicted drop of its next separating stage when that is a violation.

## Part reliability (plan 130, ADR 0156)

`packages/core/src/reliability.ts` and `packages/sim/src/reliability.ts`; rule `stock.reliability` (off; on in `stock.career-engineering`). Failure modes (`registries.failureModes`) name a module and a trigger. With the rule on, `fireStage` runs `partTrials(…, 'stage')` before each part's stage hooks and `load-vessel` runs `launchTrials` after the charge; each trial draws once per mode from the `reliability` stream (`SimCore.reliability.rng`, saved), adds 1 to the part model's experience, writes an anomaly report per failure and records the failed `(part, module, mode)`. `isFailed` is checked by `runUpdateHooks`, `runStageHooks`, `vesselAuthority`, the `action` command, `partActions` (disabled, reason `Failed: <label>`) and the comms antenna. `set-grade`, `static-fire` (needs an active building providing `test-stand`; a quarter of the part's cost), `fix-anomaly` (twice the part's cost) and `repair` (an engineer in a suit within 50 m and 2 m/s) are the commands; the grade surcharge is part of `launchCost`. `SimSave.reliability` (optional in format 5) is written once anything happened; `Snapshot.reliability` (absent when off) lists the part models that can fail, the reports and the failed modules.

## Replays (plan 131, ADR 0159)

`packages/sim/src/replay.ts`, file format in `packages/core/src/replay.ts`. `recordReplay(sim, name, { terrain })` takes the start `SimSave` and returns a recorder: `dispatch` logs each accepted command with `sim.time`, `tick()` (after each `step`) takes a checkpoint every 10 s of sim time (`checkpointOf`: per vessel id, mode, SOI, position, velocity, part count, and `n`, the commands dispatched before it), `finish(name?)` adds a final checkpoint. `verifyReplay(make, replay)` resumes the start save and, per checkpoint, dispatches its commands after stepping fixed `dt` of sim time (a wall step of `dt / warp`) to each command's time, then compares (`checkpointProblem`: discrete values exactly, numbers within 5e-3 or 1e-6 of the value). The web sim host records every flight from boot behind a `Proxy` on `dispatch` (message `replay`); `tools/replay-verify/verify.ts` verifies a file from the command line.

## Aircraft (plan 063, ADR 0161)

A module collider may carry `wheel: { rolling, grip, brake, steer }`: `collectColliders` gives its box `friction: 0` (combined with the ground by the minimum) and records it in `FlightBody.wheels`. `groundContacts` keeps each wheel's contact point with the tile, in the body's own axes; the next `prepareFrame` runs `stepWheels`: at each wheel in contact, along its rolling direction (the part's +Y turned about the ground normal by `steer` times the yaw demand) a force against the slip limited by `(rolling + brake × grip) × load`, across it one limited by `grip × load`, each taking a quarter of the slip out per step; the load is the weight shared over the wheels in contact. A design with `aircraft: true` is placed on the surface lying level, nose north and +Z up, on its lowest point along -Z (`placeOnSurface(…, level)`). `trim { vessel, pitch }` sets `VesselState.trim`, added to the pitch demand in `effectiveControl`. SAS mode `level` holds the attitude with the nose on the horizon along its heading and +Z up (`levelAttitude`), its integral allowed the whole authority.

## Comms planning (plan 118, ADR 0163)

Off the sim Worker (ADR 0101 point 2): `apps/web/src/lib/comms-planning/` and its own module Worker (`planning.worker.ts`), started by the Mission Center's Planning panel on first use and answering from snapshot data. It runs the link rule of tier 1 on conics:
- a vessel follows its conic in its current SOI;
- a station turns with its body;
- two nodes link under `√(range_a × range_b) × scale` when no body sphere crosses the segment.

Terrain, burns, SOI changes and routing are left out. The contact timeline samples every 10 s and bisects each change to 0.01 s, as `updateNetwork` does; for a vessel on rails over spherical bodies it gives the sim's link events. The coverage grid (72 × 36, equirectangular) holds the fraction of samples at which a ground receiver links to some node. `resonantDeployment` (`packages/kepler`) gives the deploy orbit of period `T (N±1)/N` with an apsis on the target orbit, the drops a deploy period apart (360°/N spacing) and the burns. A vessel's range on the page comes from its parts' `{ antenna }` configs and the `antennas` of the `ready` catalog. `boundary.test.ts` keeps the two Workers' import graphs apart.

## Design records and control from here (plan 221, ADRs 0208 and 0215)

`VesselState.design` is the launch design, copied to each piece a split makes; `Sim.designOf(vessel)` returns `{ design, parts, rebuilt }` with the design indices the vessel still has (`vessel-design.ts`; a vessel from an older save gets a design rebuilt from its parts on request, without writing it). `splitVessel` emits `vessel:split { parent, vessel, parentParts, parts }` after `vessel:created`. Snapshots give each part its design `index` and each vessel its `nextStage` and `controlPart`. `set-control-part { vessel, part | null }` accepts a part with a `controlSource` or `controlPoint` module; SAS points that part's +Y (`controlNose`: the part's rotation in the vessel axes) in flight and on rails, and the part goes with the piece that keeps it on a split.

## Time warp (plan 206, ADR 0202)

`packages/sim/src/warp-limits.ts` and `warp.ts`. Levels are `WARP_LEVELS` (core): 1×, 2×, 4×, 10× physics and 50×, 100×, 1k×, 10k× rails; a Sol world adds 100k× (`SOL_WARP_LEVEL`), n-body gravity caps at `NBODY_MAX_WARP`. `warpLimit(core)` is pure over the state: it looks at the watched vessel (`SimCore.warpFocus`, set by the `vessel` of `warp` / `warp-to`; not saved) and the flight vessels of its frame within `PHYSICS_RANGE` (without a focus: every controlled flight vessel). A vessel with the throttle up in flight allows 10× ("engine running"); one in the atmosphere and not landed 10× ("in the atmosphere"); a landed one or one on surface rails the top; otherwise the rails tier of its altitude (`warpTiers`: 50× above the atmosphere top, or 2.5 % of the radius on an airless body, then 20 %, 40 %, 80 % and 100 % of the radius: KSP's Kerbin table for the stock home). `Snapshot.warpLimit` reports it.

- `warp` is never refused for its size: it is granted `min(asked, limit)` and the result carries `granted` and, when lower, `limit` ("Max 10× — engine running"; `warp:clamped`). Up to 10× the vessels stay in flight and the loop runs whole fixed steps, so physics warp matches real time step for step. Above it `packForRails` puts every flight vessel on rails: landed ones on surface rails, others on their conic, and one nobody watches in an atmosphere is **frozen** (rails kind `frozen`: body-fixed position, ground-relative velocity and attitude; `vessel:frozen`; `Snapshot.frozen`; never reaped as debris). Below 10× again `thawFrozen` puts it back in flight where it was (`vessel:thawed`).
- Each step at rails warp `holdWarpLimit` lowers the warp when the limit fell (`warp:stopped` with the reason) and packs any vessel that came into flight. A `throttle` above 0 on a vessel on rails during rails warp drops to 10× first (`dropForThrust`) and wakes it; `wakeBlocker` and `load-vessel` allow up to 10×.
- `warp-to` takes a `time` or a `target`: `apoapsis`, `periapsis` (the next one, from the elements, 15 s early), `soi` (the next change of sphere on the predicted path, 15 s early), `node` (30 s before the earliest node); `alarm` (its time, plan 224). With vessels in flight it runs at physics warp and ends within one fixed step of the time.

## Fleet management (plan 223, ADR 0208)

`packages/sim/src/fleet.ts`. Every vessel has a type for the fleet list (`VESSEL_TYPES`: debris, probe, rover, lander, ship, station, base, plane, relay, eva, flag): the player's (`set-vessel-type`, `VesselState.type`, saved with the vessel) or a guess from its parts (`guessVesselType`: a kept part is a flag, a part that walks a suit, no control source debris, then wings a plane, rover wheels a rover, legs a lander, seats a ship, else a probe), in `VesselSnapshot.type`. `rename-vessel` trims and keeps 60 characters; `terminate-vessel` removes the vessel like a crash (reason `terminated`), so its crew follow `stock.crew-death`. Recovery (`quoteRecovery`, core `recoveryFactor`) pays 100 % within 200 m of a site, 98 % within 3 km, then falls linearly to 10 % at the far side of the body; every site of the world on the home body is a recovery site, and any landed or splashed vessel at rest can be recovered, flown or not.

Plan 318 (ADR 0274): `VesselSnapshot.atSite` (`siteSpotOf`) gives where a vessel stands at a site, in metres east and north of its centre (the plane of `SitePad` and `placement.at`), while its centre of mass is within the site's flat radius and below `PAD_CLEAR_HEIGHT` (100 m) above the ground. Before a launch at a site, Flight treats every vessel within `PAD_CLEAR_RADIUS` (40 m) of the launch spot as an occupant and asks Recover, Terminate or Cancel; `load-vessel` itself never refuses for an occupied pad. `clear-debris { site? }` terminates every debris vessel (`isDebris`), or with `site` only those on its body within its `flatRadius` of its centre.

## Alarms (plan 224, ADR 0223)

`packages/sim/src/alarms.ts`. `add-alarm` sets a user alarm (`alarm.<n>`; with an `id` it replaces that one) and `remove-alarm` deletes one; `Snapshot.alarms` lists them in time order and `SimSave.alarms` (`{ next, list }`, optional, no format bump) keeps them. A `time` or `transfer` alarm takes its time from the command; an `apoapsis`, `periapsis`, `soi` or `node` alarm takes the vessel's next such event from `eventTime` (shared with warp-to) less `lead`, or less the warp-to margin. The time is fixed when the alarm is set. While the warp is above 1 the step stops at the earlier of the warp-to target and the next alarm (`stopAt` in `sim.ts`), so the clock lands on it on rails and within a fixed step in physics warp; `fireAlarms` then sets the warp to 1, emits `warp:stopped` (`alarm "<name>"`) and `alarm:fired`, and drops the alarm. Alarms do not care which vessel is watched, so a background vessel's alarm stops the warp like any other.

## Pause and warp-stop events (plan 205, ADR 0201)

`pause { on }` sets `SimCore.paused` (not saved: a loaded world runs); `Sim.step` returns at once while it is set, and `Snapshot.paused` reports it. A pause is refused when the stock rule `stock.pause-allowed` is false (Career Hardcore); warp is not a pause and stays allowed. `warp:stopped { reason }` is emitted when the sim ends a warp by itself: a controlled vessel changed sphere of influence (only when the warp was above 1), a warp-to arrived, a vessel in flight cancelled a warp-to, or a user alarm came (plan 224).

## Debug tools (plan 203, ADRs 0200 and 0213)

`packages/sim/src/debug.ts` and `cheats.ts`. Who may use them is the stock rule `stock.debug-tools` (`always` in Sandbox, `opt-in` in Science and Career, `locked` in Hardcore; not changeable; a world without the rule counts as `always`). `dispatch` refuses every `debug-*` command except `debug-mode` with `debugRefusal`'s reason unless the access is `always`, or `opt-in` with the mode on. The state is `WorldInfo.debug` (`{ mode, usedCheats, cheats }`, optional, so saves stay format 8): `debug-mode` switches the mode in an `opt-in` world (refused where it is `always` or `locked`), and it and every accepted debug command set `usedCheats` for good. `debug-cheat` switches one of `DEBUG_CHEATS`; the other files read them through `cheatOn`/`infiniteResource`:
- `withdrawResource` grants the draw without touching the stores (`infinite-electricity`: `stock.electric-charge`; `infinite-monopropellant`: `stock.monopropellant`, `stock.eva-propellant`; `infinite-fuel`: every other resource);
- `damagePart` (`no-crash-damage`) and `burnPart` (`ignore-temperature`) return early;
- `controlFor` and `signalRefusal` give full control (`comms-without-signal`);
- `lifeSupport` uses nothing and ends shortages (`infinite-life-support`);
- `construction` builds at once (`instant-construction`); `unbreakable-joints` has no reader yet.

`debug-grant` books funds, science and reputation as ledger entries with cause `debug.grant` and with `tech` researches every node. `debug-set-orbit` takes the vessel out of flight (or spawns `design`) and puts it on rails at the elements with epoch now (refused below the surface); the normal wake path brings it back to physics. `debug-set-location` lands it with `placeOnSurface` (a site's pad, or latitude and longitude) or, with `kind: 'air'`, puts its centre of mass at the altitude above the reference sphere with the ground-relative velocity (`airState`: speed along the heading from north at the climb angle, plus the body's spin), then enters flight at warp 1 (on no free frame it goes back on rails where it was). `debug-set-resource` fills each matching store and withdraws down to `fraction` of its capacity or to `amount`; `debug-set-temperature` and `debug-set-crew-level` set the values. `Snapshot.debug` reports `{ access, mode, allowed, usedCheats, cheats }`.

## Snapshots and commands (sim ↔ host protocol)

Types and zod schemas are in `packages/core/src/protocol.ts` and `protocol-schemas.ts`; plain data, so the same protocol works in-process and over `postMessage`.

```ts
interface Snapshot { t: number; vessels: VesselSnapshot[]; bodies: BodySnapshot[] }
interface VesselSnapshot {
  id: EntityId; mode: 'flight' | 'on-rails'; soi: BodyId;
  position: Vec3; velocity: Vec3; orientation: Quat;   // root part origin / velocity / attitude, BCI
  parts: PartSnapshot[];
  orbit?: OrbitalElements;                              // of the centre of mass; absent for near-parabolic/radial
  surface?: boolean;                                    // on surface rails (ADR 0024)
  terrainHeight?: number;                               // m above the sphere under the root; only with a terrain field (ADR 0043)
  sas?: { mode; reference; error /* rad */ };           // stability assist (ADR 0049)
  name?: string;                                        // the vessel's name (plan 035)
  target?: TargetSnapshot;                              // { kind, id, name, position, velocity (target minus vessel, shared inertial axes), distance, relativeSpeed, approach: { time, distance, relativeSpeed } | null } (ADR 0065)
  nodes?: ManeuverNodeSnapshot[];                       // maneuver nodes in time order (ADR 0056): { id, time, prograde, normal, radial, dv, body?, vector? } = the burn that is left
}
interface PartSnapshot { id; definition; position: Vec3; orientation: Quat; modules: Record<string, unknown>; temperature?: number /* K */ }
interface BodySnapshot { id: BodyId; position: Vec3; rotation: Quat }   // rotation = turn about +Y since t = 0
type Command =
  | { type: 'throttle'; vessel; value }            // 0..1
  | { type: 'attitude'; vessel; pitch; yaw; roll } // each -1..1, about body +X, +Z, +Y
  | { type: 'stage'; vessel }
  | { type: 'sas'; vessel; mode?; reference? }       // mode off|hold|prograde|retrograde|normal|antinormal|radial-in|radial-out|maneuver|target|anti-target; reference surface|orbit (ADR 0049)
  | { type: 'action'; vessel; part; module; action; args? }   // args array is spread; a single value is wrapped
  | { type: 'warp'; factor }                       // 1..1e6
  | { type: 'warp-to'; time; factor }              // eases down and lands on `time` with warp 1 (ADR 0056)
  | { type: 'node-set'; vessel; id?; time; prograde; normal; radial }  // create (result carries `node`) or replace a maneuver node (ADR 0056)
  | { type: 'node-remove'; vessel; id? }           // one node, or all
  | { type: 'target-set'; vessel; target: { kind: 'body'; id } | { kind: 'vessel'; id } | null }   // aim at a body or another vessel; null clears (ADR 0065)
  | { type: 'load-vessel'; design; placement? };   // surface (default lat 0, lon 0) | state (COM position/velocity, BCI)   // surface latitude/longitude are body-fixed (plan 025)
```

- **Part frame (precise):** `PartSnapshot.position` = part origin − vessel root origin, **in BCI axes** (already rotated by the vessel's attitude, not in the vessel body frame); `PartSnapshot.orientation` = the part's absolute orientation. This is what the renderer applies today (`scene.ts` `syncParts`), so no renderer change was needed. `VesselSnapshot.position` is the root part's origin, not the centre of mass.
- `throttle`, `attitude`, `sas` and `stage` need a control source (`ModuleDefinition.controlSource`). `dispatch` validates with `commandSchema` and refuses with a reason; semantic refusals cover unknown vessels/parts/modules/actions, exhausted stages, bad designs, warp rules and a missing physics frame.
- A snapshot of the two-stage vessel is about 2.8 kB of JSON and takes about 5 µs to build; a flight step of that vessel costs about 56 µs (Bun, Rapier compat; measured before rigid grouping, a 100-part stack now costs about 145 µs per step, see journal 011), so 50 Hz stepping uses well under 1 % of a core and a snapshot per rendered frame is cheap.

## PhysicsBackend (`packages/core/src/physics-backend.ts`)

Interface in core (additive changes by plan 011: a `compound` `BodyShape`, `MassPlacement` — `centerOfMass`, `inertiaFrame` — in `BodyDesc` and as a fourth `setMass` argument; `getTransform` is the body origin, velocities are the centre of mass's; the sim creates no joints any more but `createFixedJoint` stays in the interface; additive by plan 012: `BodyDesc.friction` / `restitution` and `contacts(a, b)` returning `{ shape, point, distance }` contact points after a step, none in the mock), `@orbital/physics` implements it (`createRapierBackend({ solverIterations? })`, async; `createMockBackend()`). Contract points the sim honours: everything in the local frame; forces last one step, so gravity, thrust, drag and torque are re-applied every step; `Velocity.angular` is about local-frame axes; impulses (decoupler ejection) are applied as direct velocity changes because the backend only has one-step forces. The mock backend ignores joints, collisions and the centre-of-mass offset and is only suitable for hook-level tests.

## Save and resume (plan 043, ADR 0050)

`sim.save()` returns a `SimSave` (`@orbital/core`, `save.ts`): `format`/`formatVersion` (6; each older version migrates by `SIM_SAVE_MIGRATIONS[n]`, frozen fixtures `test/fixtures/save-v1.json` to `save-v5.json`; 5 to 6 (plan 122) names the save's `home`, which was `bodies[0]` before: 1 to 2 the body list and frame `soi`, 2 to 3 maneuver nodes and `warpTarget`, 3 to 4 vessel targets, 4 to 5 the world info), `apiVersion`, the booted `mods` (id, version), `bodies` (ids of every body, root first), `dt`, `seed`, `time`, `warp`, `warpTarget`, `accumulator`, `rng` state, `worldInfo` (format 5, plan 077, ADR 0110: the world the run belongs to, below), optional `worldTick` (plan 082, ADR 0171: `lastDay` and each world-tick system's stream state; a save without it derives the day from `time` and starts fresh streams, so it fires no duplicate tick), `world` (`world.serialize()`: vessels, parts, module states, SAS, rails, temperatures, counters), `frames` (per physics frame its `soi`, origin, velocity and, per body in creation order, the pose of the body origin, rotation, linear and angular velocity and the mass properties last pushed to the backend) and a `checksum` of the rest. Call it between steps. It changes nothing except bringing `background` closed forms up to the save's time (plan 082), which a later tick would have done the same way.

`createSim({ resume })` validates the save like a file (`readSimSave`: marker, version, checksum, migration chain, schema; then the sim components, registered parts/modules/bodies, every flight vessel in exactly one frame body), restores the world, clock, accumulator and PRNG, and **rebuilds** each Rapier body with the saved pose and mass properties (`createVesselBody`); ground tiles and stone bodies come back at the next step. Failures are `SaveError`s with a `code` and a message for the player. The step `dt` and the root body must match the save; the plugin ids must be loaded (versions may differ). State a plugin keeps in closures outside the world is not saved.

**World info (format 5, plan 077, ADR 0110).** `createSim({ world })` takes a `WorldInfo` (`id`, `seed`, `systemId`, `systemVersion`, `variant`, `gravityModel: "patched"`, `epoch: { day, fraction }`, `rules`, `sites`), validated by `worldInfoSchema` (`n-body` is refused: "n-body worlds are not available yet"). Without it a new run is the **Legacy world** (`legacyWorldInfo`: id `"legacy"`, the run's seed, stock at its booted version, `default` variant, fictional day 0, no rules, no sites), and a resume keeps the save's world; `world` with `resume` must name the save's world (`incompatible` otherwise). The sim holds it on `SimCore.info`, beside the entity world (no entity, so entity ids are unchanged), exposes a frozen copy as `sim.worldInfo` and writes it as `SimSave.worldInfo`. Migration 4 to 5 gives an old save the Legacy world with its own seed and the stock version it lists. `readSimSave` signs every result over the schema-ordered parsed data (after checking the raw bytes), so a second read (the storage layer, then `createSim`) checks its own bytes even when a migration or a schema default changed it. **Rules (plan 078, ADR 0111):** `worldInfo.preset` and `worldInfo.changelog` (defaults `stock.sandbox` and `[]`) sit beside `rules`; `createSim` stores the resolved value of every registered rule, `set-rule` changes one at dispatch (effective from the next step), appends to the changelog and emits `world:rule-changed`; since plan 230 (ADR 0230) a change must go toward the rule's `easier` direction (`ruleChangeProblem` in core: a boolean's easier value, a number's `higher`/`lower`, an enum's hardest-to-easiest order; a rule without it is fixed once the world is made) unless the world's debug tools are on (`debugAllowed`: Sandbox always, Science and Career with Debug mode); `Snapshot.rules` and `SystemContext.rules` read them.

**World tick epoch (ADR 0114, amending ADR 0171).** The tick day is the calendar's day (`tickDayLength`: `calendarOf` of the sim's system, read on the root; stock 21 650.8 s, the solar day of a planet turning in 21 600 s round the Sun since plan 122) and the epoch is read in SI days from J2000.0: `day(t) = floor(((epoch.day + epoch.fraction) × 86 400 + t) / dayLength)`, the same as before at epoch 0.

**Buildings (plan 090, ADR 0115).** Sites carry optional `buildings` and `roads` (in `WorldInfo.sites`, additive). `place-building { site, kind, cell, rotation, id }` and `remove-building { site, id }` (`packages/sim/src/buildings.ts`) validate with core's `canPlace`, add the completed road cells, and write an implicit Legacy site (an empty `sites` list) into `WorldInfo.sites` the first time. `Snapshot.sites` lists each site's buildings and roads. Instant until plan 096 adds cost and construction time.

**Economy (plan 095, ADR 0113).** `SimCore.economy` holds `{ balances, entries }`, saved as the optional `SimSave.economy` (absent: a fresh ledger with funds from `stock.starting-funds`). `packages/sim/src/economy.ts`: `load-vessel` checks and debits `designCost × stock.cost-multiplier` (cause `economy.launch`); `recover-vessel` is accepted on surface rails or landed at rest, credits the live value (part costs plus current store contents) times `recoveryFactor(d)` to the nearest recovery site (until 084 the launch site) and removes the vessel; on each world tick `economyTick` writes the registered charges and, every 30th day, the reputation decay. Nothing is written while `stock.economy` is off. `Snapshot.economy` carries the balances, `VesselSnapshot.recovery` the quote while a vessel can be recovered. A career bot (`test/helpers/career-bot.ts`) runs 3 600 days of launches and recoveries in about 3 s.

**Markets and production (plan 097, ADR 0124).** `packages/core/src/market.ts` (commodity and recipe schemas, `marketTick`, `rawPrice`) and `packages/sim/src/market.ts`. `SimSave.economy.markets[commodity] = { price, stock, history }` and `.storage[site][commodity]` are optional; a market opens at its base price and target stock on the first tick or trade with the economy on. A buy takes units out of the market stock at today's price, a sale adds them; each world tick, after the day's charges (`marketDay` in `tick.ts`), every working building with a recipe adds its outputs (scaled by its level's `production` capacity) to its site's storage up to the `storage` capacity, unless funds are below zero, then each traded market relaxes its stock toward the target and moves its price toward `base (target / stock)^elasticity` by at most `cap` a day, clamped to `[floor, ceiling] × base`. `load-vessel` with markets open quotes the parts (and contents no commodity covers) at their static price and the propellants from the launch site's storage first, then the market (`economy.launch` plus one `stock.market-buy` per commodity). `market-buy` and `market-sell { commodity, amount, site }` trade traded commodities only. `Snapshot.economy.markets` and `.storage` feed the Space Center's read-only Market panel.

**N-body worlds (plan 125, ADR 0122).** `packages/sim/src/nbody.ts` and `packages/kepler/src/nbody.ts`. In a world with `gravityModel: 'n-body'` every rails state made for a vessel off the ground is `numeric` (`{ r, v, t0, h }` in its sphere's body frame). The field of a frame is every other body, positioned from the body paths (`systemPosition`), with the indirect term. The rails advance by accepted Bulirsch–Stoer steps (`nBodyStep`, cached per rails record and recomputed to the bit after a resume) and are read between steps by quintic Hermite. Sphere changes are frame changes (the same crossing code). In flight the other bodies' pull at the frame origin is added to every vessel. Warp is refused above `NBODY_MAX_WARP` (1e5) and halved while a frame spends more than `NBODY_FRAME_EVALUATIONS` (5 000) acceleration evaluations (`warp:limited`). `createSim({ ephemeris })` gives bodies with a `naif` id a `table` path on JPL's DE440 within the asset's span.

**Off-world bases (plan 128, ADR 0125).** `packages/sim/src/bases.ts`. `deploy-base { vessel, id, name }` takes a landed vessel at rest with a `stock.base-kit` module on a body other than home, founds a `base` site there through `foundSite` with the hub layout, and removes the kit (`deployed`). Craters ground reads the zones of its sites (`zonedMoonHeight`: each zone blends toward the raw height at its centre), from the next load like any founded site. `join-site { vessel, site }` adds a landed vessel within the flat radius to `Site.members`; `membersTick` on each world tick drops members that are gone, not landed at rest, or beyond `flatRadius + blendWidth`. In `marketDay`, before the recipes, each member's `stock.drill` modules add ice to the site's storage; recipes consume their stored inputs (the share of a day the inputs allow). `create-route` needs a `landing` milestone on the destination's body; `routesTick` runs each route whose window has come (`windowDays`: the child's period, or the synodic period of the ancestors that share a parent), moves the cargo (buying the shortfall at the market from a home site) and books the launch-service price plus the bought cargo (`stock.supply-route`). Routes live in `SimSave.economy.routes`.

Equality with an uninterrupted run: byte for byte for flight in free space, on rails (orbital and surface), through staging and during an SAS hold; within 5e-3 (m, m/s, rad, K) while a body touches its ground tile, because the contact solver's warm start is private to Rapier and a rebuilt body starts cold (`test/resume.test.ts`, ADR 0050 point 4). New sim state must be added to the world (or to `SimSave` with a version bump and migration) and to the resume tests.

## Determinism

Fixed `dt`, seeded PRNG, no clock, entity creation and Map iteration orders fixed (ascending ids), Rapier creation/removal order identical: `test/determinism.test.ts` runs a command script (throttle, attitude, a stage that splits the vessel) twice and compares the JSON snapshot and the serialized world at t = 100 s byte for byte. Rapier is deterministic on the same build; cross-machine determinism is not a goal.

## Known limits (MVP)

Rigid vessels (no flex), patched conics only (no n-body: a vessel feels one body at a time, the moon does not pull the planet), radial attachment by yaw only (no tilted parts), lift only from fin-like modules, simplified heating (windward area only, no conduction), terrain heights only where `createSim({ terrain })` supplies them, no collision damage between vessels, one physics bubble of 2.5 km (second far vessel in flight is refused), attitude is frozen on rails, reaction-wheel torque acts on the wheel's own body.
